# One-click stable release (implementation, not yet published)

Branch: `0die/add-one-click-release-workflow-0600f9f0`0. Worktree: `0/Users/sharath/.die/worktrees/die-f528e86af6b5-task_0600f9f0`0. Based on fetched origin/develop 88c2d70 (includes PR #6). GitHub reports develop as the repository default branch.

On a phone: GitHub repository → Actions → Release → Run workflow → select **develop** → Run workflow. No inputs. Watch the **same run** through Publish; a prepared commit is not a completed release. Requires Actions to have permission to write contents and branch rules to permit the GitHub Actions bot to update develop and create tags. Do not choose another branch/tag. If branch protection rejects the push, it fails closed before gates and requires repository configuration or a normal reviewed preparation commit; there is no bypass.

The dispatch job fetches latest develop, refuses to run a different release workflow revision, selects an already-prepared stable version when ahead of the latest stable tag or bumps the patch of the greater of package version and latest stable tag. It writes missing notes from commit subjects since the last tag (existing hand-written notes are preserved), commits package.json and notes to develop, then passes the exact resulting SHA and version tag through all native, Linux/web, updater, macOS, checksum and licensing gates. The ordinary develop dry run and tag-push release paths remain; dispatch does a full build because its bot-authored preparation push cannot trigger the dry-run workflow. It does not treat unrelated CI as release verification. Serial dispatch concurrency and fast-forward push prevent overlapping requests from silently overwriting one another. Before publication it confirms develop still points to the tested SHA; an absent tag is pushed and a same-SHA tag is reused (a different SHA fails). It creates a draft release with the same 12 assets, verifies their sizes and SHA-256 digests, and only then publishes it. GitHub's GITHUB_TOKEN pushes do **not** trigger the push-tag release workflow; publishing within this run is deliberate.

Notes generated from commit subjects are a baseline, not edited release prose; review them before choosing to publish if special wording is required. If gates fail, the preparation commit stays on develop but no tag is made; rerun after fixing develop. If tag push or draft upload succeeds but publication fails, open that failed Actions run on the phone and choose **Re-run failed jobs** while the run's staged artifacts are still retained. The gated publish retry accepts the same-SHA tag, fills missing draft assets, checks every asset digest/size and exact set, then publishes. A complete published release is verified and left unchanged. A conflicting tag, changed develop, changed asset, extra asset, or incomplete already-published release fails closed for investigation; do not launch a new dispatch to repair the failed run. If develop advances during verification, publish fails closed; run again on latest develop. A later PR may need to update the GitHub workflow file before manual dispatch if it changed since the clicked ref.

Values assessment: preserves exact artifact proof and existing release gates (values 1, 2, 9); refuses stale/duplicate publication rather than hiding failure (8); keeps mutation and testing in one workflow without a second trigger/token mechanism (6, 7). Values unchanged; this is a local release recipe, not a new general principle. No remote hosted execution or real publication has occurred in this branch.
