# T3-v2 production migration — requirements and regression audit

**Status:** independent read-only source audit, 2026-09-21. This wisdom file is the only file changed. Product source, canonical patch/checkouts, and tests were not edited or run.

## Baseline and interpretation

The production baseline is current root source plus pinned T3 719a76ca1dbf5490f1aa33ffb9966301e02be9a9 and web/t3.patch. The authorized migration may move **web delegation** to T3 orchestration-v2 child threads. It cannot silently redesign the root CLI or erase shipped Die behavior. Reviewed sources: README.md, PRODUCT.md, current source/tests, the canonical patch and patched pin, and the web/mode/history/compaction/cost/handoff/lifecycle/security/packaging notes.

Upstream v2 is not a task-widget swap. PR #2829 has a durable thread/run graph, scoped MCP delegate_task/task_status/task_cancel, separate child Pi processes/sessions, result transfer/ACK, replay/reconnect, and navigable child transcripts. Current production instead runs Die's execute helper and projects bounded local TaskManager start/completion records. Cannot swap one API for the other.

## Serious semantic mismatches — a helper swap is not enough

1. **subagent() is not delegate_task.** Die has profiles, model/thinking, batches, waitSeconds versus timeout, parent job IDs, cursor inspection/input/stop, exact depth rules, persisted sessions, attention/completion, and nested synchronous leaf behavior. Upstream creates a durable T3 thread/run with scoped auth, ACK/replay and native cancel/status. Every semantic needs an explicit mapping.
2. **Two ACK systems can duplicate or lose results.** Die completion custom messages and v2 transfer can both wake the parent. Terminal state, model delivery and UI display need one owner/idempotency key across the delivery-before-ACK crash window.
3. **Direct MCP exposure breaks shipped tool/depth policy.** Die intentionally activates execute only. Adding mcp__t3-code__delegate_task creates a second route and bypasses execute profile/depth/job checks. The experiment's duplicate prevention was guidance-only.
4. **Cancellation domains differ.** Die process/job IDs and T3 task/thread/run IDs have different ownership/lifetimes. Parent abort, selected local stop, selected child cancel are not synonyms.
5. **T3 lineage is not Die lineage.** Native child sessions will not automatically carry Die parent/depth/profile metadata. Without a mapping, workers may delegate, Herdr sees roots, /resume identity is wrong, and cost omits/double-counts children.
6. **Generic Pi RPC launch can bypass session/compaction behavior.** Omitting current allocation/lease/validation, /mode preflight, compaction continuation or usage refresh breaks history, shake, mode and cost even if chat works.
7. **Component success is not packaging proof.** V2 adds migrations/services/cache materialization. Only the relocated final executable proves runtime completeness and Bun PTY selection.

## Shipped scope versus old undecided TODOs

Required: root CLI and one-execute behavior; web model/mode; execute/handoff/completion display; local lifecycle/attention/inspect/cancel and Stop; profile/depth; history/shake/compaction/context/cost; Herdr stability; loopback security; one-file Bun/PTy/updater; and, for this migration, durable T3 child/status/cancel/transcript with exactly-once delivery.

Do **not** silently add: full local-job logs/progress in web, a global task broker/tree/root service; global concurrency or new output budgets; automatic memory consolidation (manual only); persistent execute REPL; /ps phase-2 UI; ask-user/API-help proposals; LAN no-auth; updater redesign; ordinary sidebar rows for every child (relationship/Agents navigation can satisfy transcript access); stdout/stderr separation; global TTL/deletion; paid-provider behavior. Project memory remains filesystem-based with cooperative writes; whether native children share more than this is a decision, not implied scope.

## Product decisions required before merge

1. **Web route:** Does existing subagent() transparently route to v2, or is a separate execute helper approved? Direct model-visible MCP changes the one-tool contract.
2. **Profiles:** Exact profile→v2 model/thinking/role/runtime mapping; child mode inheritance; authoritative depth claim.
3. **Completion owner:** V2 transfer or Die completion notification wakes native parent. The other can only be telemetry.
4. **Job API:** Native IDs in jobs.list/inspect/stop as tagged entries, or separate native status/cancel? Preserve local semantics; input/closeInput do not naturally apply to threads.
5. **Costs:** Die persisted combined total, T3 thread aggregate, or both with distinct labels. Never sum aggregate totals.
6. **Herdr:** Reporting process and bridge from native child liveness to it.
7. **Navigation:** Agents/relationship transcript entry is sufficient unless ordinary sidebar placement is explicitly requested.
8. **Memory:** Automatic consolidation remains out of scope; decide only whether native children require extra coordinated sharing.

- Port current Pi/model/mode/Stop/timeline/security/PTY regressions.

- Final compiled executable, private HOME/cache/random loopback, no runtime node/bun/npm: model switch, every mode, execute+handoff, local completion/attention, native child launch/open/cancel/reconnect, delayed terminal input/resize, shutdown.

- Stress bounded child/event/replay state and process scan for owned descendants.
- Pin exact upstream v2 commit and patch checksum; test migration from prior production state and fresh state.

## Immediate review warning on the in-progress helper bridge

A read-only look at the concurrently appearing src/tasks/t3-task-backend.ts confirms the helper-swap risk is already concrete:

- It calls delegate_task with role equal to fast/normal/orchestrator, but upstream #2829's documented role enum is implementation/research/review/design/test/general. It also sends target.profile, target.thinking, cwd, depth and parentTaskId, none of which exist in the documented DelegateTaskInput. Depending on schema excess-property handling this either rejects immediately or silently discards the only attempted profile/depth policy. target only supports providerInstanceId, driverKind and model. Do not call this policy-preserving.
- Upstream result text is summary/latestTerminalSummary plus transfer identifiers. The current parser looks only for output/result/message (or flattened text content), so a completed native child can become a completed Die job with no final answer. Preserve childThreadId/run/node/transfer IDs; reducing the response to taskId/status loses navigation and exactly-once delivery evidence.
- It generates a fresh clientRequestId inside each delegate call with no durable request record. If the server accepted the request but the response is lost/times out, the caller cannot replay the same key and can create a duplicate child.
- It polls task_status every 1 second and swallows every poll error. That does not meet durable subscription/reconnect or truthful attention requirements: disconnection can leave a forever-running adopted job with no surfaced fault, while every child adds timer/network churn.
- shutdown clears timers/records and closes the MCP client. Verify ordering with TaskManager external cancellation and remote child settlement. Otherwise parent shutdown can orphan a T3 run or discard completion. MCP DELETE closes a client session, not necessarily the child run.
- Mapping native tasks into TaskManager is viable only if metadata is extended, not erased: native childThreadId/run IDs, profile/depth, durable request key, source kind, and transfer/ACK state are needed. Input/closeInput must continue to reject native jobs explicitly.

These are P0 integration blockers, not polish. Conformance tests should use the exact pinned upstream tool schemas rather than a permissive mock accepting invented fields.
