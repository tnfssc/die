# GPT-Live WS local speech/interruption review (2026-09-24)

Scope: HEAD `src/live/gpt-live-playback.ts` and `src/live/extension.ts`; documentation and package metadata fetched publicly, no paid API, device access, or runtime VAD validation. This is a local playback policy review, **not** a parity or production barge-in claim.

## Official evidence and its limits

- [OpenAI GPT-Live primary WebSocket guide](https://developers.openai.com/api/docs/guides/voice-websockets?api=live): receive `session.output_audio.delta` and queue decoded audio for playback in order; track playback in the **application** audio queue. The primary WS has no output timing fields or output-audio-done event; input appends have no acknowledgement. Its Node/Python PCM examples stream audio and print/write received bytes, **not** a recommended microphone VAD or interruption algorithm.
- [GPT-Live managing conversations, audio output](https://developers.openai.com/api/docs/guides/live-conversations#audio-output): full duplex, transcript timestamps are separate from playback; WS audio lacks timing and output-done. [Idle/restart section](https://developers.openai.com/api/docs/guides/live-conversations#manage-idle-time) describes optional *application-managed* local speech detection for restarting a closed session and buffering opening speech, not a named library or verified in-session barge-in method. The server can continue speech or delegated work while input is muted; use application player/capture controls separately.
- [GPT-Live server controls, check speech before playback](https://developers.openai.com/api/docs/guides/voice-server-controls?api=live#check-speech-before-playback): for an **output guardrail** workflow, implement application output VAD or framework noise gate to find candidate segments; GPT-Live provides neither for that workflow. Associate checks/audio/playback with app-generated IDs; on interruption clear buffered/queued audio and ignore late approval. Output VAD is **not** a recommendation for input speech detection and cannot establish whole-answer completion. This guide discusses buffering/approval, not an official mic VAD package or universal cancellation protocol.
- [OpenAI SDK Live event types](https://github.com/openai/openai-node/blob/master/src/resources/live/live.ts) and [GPT-Live delegation guide](https://developers.openai.com/api/docs/guides/live-delegation?delegation-mode=client): useful wire/event references, not a reference implementation of mic VAD, local speaker-echo cancellation, or old/new output epochs. Realtime API's server VAD and response-cancel examples must **not** be transplanted to this different GPT-Live WS contract. No official GPT-Live WS client-side microphone VAD dependency, thresholds, interruption epochs, or guaranteed new-response audio boundary was verified in these sources. Absence in reviewed sources is not a proof no such recommendation exists anywhere.

## Dependency decision

A plausible small alternative is [`@echogarden/fvad-wasm`](https://www.npmjs.com/package/@echogarden/fvad-wasm), [source](https://github.com/echogarden-project/fvad-wasm): libfvad/WebRTC VAD compiled to WASM, npm latest 0.2.0 published 2024-10-26, unpacked size ~37.7 KB, no declared runtime dependencies (npm registry metadata checked 2026-09-24). The [underlying libfvad](https://github.com/dpirch/libfvad) accepts 10/20/30 ms PCM16 at 8/16/32/48 kHz; current processed 16 kHz / 20 ms frames fit. But this package is labeled intended for Echogarden, not proven maintained on this project's Bun + packaged Linux/macOS path; no native test or false-positive/echo evaluation performed. [`webrtcvad`](https://www.npmjs.com/package/webrtcvad) and [`node-vad`](https://www.npmjs.com/package/node-vad) are native bindings whose npm latest releases date to 2019. [`@ricky0123/vad-node`](https://www.npmjs.com/package/@ricky0123/vad-node) latest 0.0.3 (2024) describes **non-realtime** Node VAD and depends on onnxruntime-node. None is a verified small **maintained** drop-in for this runtime. Do not introduce a native backend or neural model merely to rename the current heuristic “VAD”; if accuracy is required, independently test the WASM candidate and echo/device behavior first.

## HEAD behavior and narrow findings

- `GptLiveSpeechDetector.observe` requires a 640-byte 20 ms processed PCM16LE mono 16 kHz frame; RMS >=0.032 (~-30 dBFS) for four consecutive frames enters activity (80 ms); RMS <0.013 (~-38 dBFS) for fifteen consecutive frames ends it (300 ms). This measures acoustic energy, **not speech**, speaker identity, or echo. Device gain, quiet speech, background noise and assistant leakage can miss/false-trigger. There is no microphone gating: extension calls capture then always `appendMicrophone(pcm)`. Native processing is not proof of effective echo cancellation.
- On detected activity after any prior output, `capture` suppresses playback, increments generation, drops pending frames and flushes native output. First output arriving **while** activity is already detected also suppresses; speech that begins and ends **before** first output does not latch. There is an unavoidable first ~80 ms detection delay plus player/in-flight audio. `outputSeen` never clears when playback drains, so a later user utterance after an already-finished answer also latches until restart: conservative false interruption/availability cost, not a proven active-output overlap. Detection can latch on an echo or loud noise. Activity below threshold can allow stale audio through. Valid output gets a local scheduler turnComplete *per chunk* solely to drain short frames, not a provider turn boundary.
- Muted output remains dropped after quiet; `resetForFreshResponse` is unused by extension. User gets explicit “/live stop then /live start and retry” notice, new session provides the practical boundary. New mic audio continues to old WS and backend work is not canceled. Extension's playback `onError` instead stops the whole Live session on overflow/write failure (rather than leaving it latched awaiting retry), consistent with failing closed but worth describing accurately. The queue cap is 9,600 bytes (~200 ms @24 kHz PCM16) plus player/in-flight reserve, not a guarantee that no already accepted audio sounds. No remote epoch attribution or remote cancellation.
- This policy is defensible as an **honestly labeled, conservative local mute-and-restart fallback** for users who tolerate manual retry and occasional false pause. It is not robust automatic conversational barge-in or a validated VAD. Preserve explicit notice and mic forwarding; prioritize real-device echo/quiet-speech and opening-overlap testing before any usability/parity claim. No major backend change is necessary for this limited policy.

Offline existing tests: `tests/gpt-live-playback.test.ts` covers thresholds, latch/flush, quiet/reset and overflow; extension tests cover wiring. Tests do not measure real capture/echo or spontaneous fresh server output. They were not rerun here (Bun binary unavailable through this worktree's untrusted mise shim); review is source/static plus public docs.
