# GPT-Live local interruption helper (experimental)

The native audio helper emits **processed PCM16 mono 16 kHz, exactly 20 ms (640 bytes)**. Playback accepts 24 kHz PCM16 mono. There is no trustworthy user-speech signal from output chunks or delayed transcript fragments. The reviewed native WS design calls for local interruption and a 100–250 ms bounded playback queue; no deterministic old/new server output boundary exists.

## VAD choice

WebRTC's open-source audio processing VAD accepts 10/20/30 ms signed 16-bit mono frames at 8/16/32/48 kHz, so the existing processed 16 kHz capture is structurally suitable. However this codebase has no WebRTC VAD runtime. Node bindings require platform native binaries/build tooling (and maintenance/security scrutiny); neural browser VAD packages such as `@ricky0123/vad-web` add ONNX/WASM/model loading and a second capture pipeline, not a small, verified dependency for this native helper. No GPT-Live documentation establishes a required or reliable client-side VAD implementation. Avoid adding a platform-specific backend or unreviewed dependency just to claim speech recognition. A proper maintained WebRTC VAD binding plus echo tests would be a separate integration.

The present detector is intentionally **not voice activity classification**: 4 consecutive 20 ms frames above RMS 0.032 (~-30 dBFS) start activity; 15 consecutive frames below RMS 0.013 (~-38 dBFS) end it. These thresholds and timing are explicit policy, not accuracy claims. Noise, near-field echoes from the player, silent/quiet speech, compression, device gain and processing can cause misses or false trips. In particular native capture diagnostics do not prove acoustic echo cancellation. Call capture() for every capture frame and ALWAYS forward that same PCM to the server regardless of local detector state. Test on real devices before using as a barge-in guarantee.

## API / integration

Use `GptLivePlaybackRecovery` only on the GPT-Live WS path. Construct with `send(frame, generation)`, `flush(generation)`, and `onError` backed by the native player; call `start()` when native audio is ready, `capture(pcm16_16k_20ms)` on every processed mic frame and `output(pcm16_24k)` on output. `capture` returns started/ended transitions, not individual peaks. The existing `PlaybackScheduler` paces output and the GPT-Live wrapper caps pending PCM to 9,600 bytes (200 ms). Its native ring may hold additional audio (~80 ms reserve), and a write already accepted by the OS cannot be physically retracted. On detected speech it advances generation and flushes player immediately, drops queued output and latches output off; overflow and scheduler errors also fail closed. `needsRetry` identifies that latch. `resetForFreshResponse()` is allowed only once mic activity has ended, and only after caller **actually established fresh output attribution** (e.g. new session/discarding old response): it is not a WS acknowledgement, silence, or transcript completion. Do not call it on merely quiet mic; otherwise stale chunks can sound like the answer to corrected speech. The helper cannot identify whether server speech was old or new. Reconnect/request explicit retry when unsure. `close()` when done.

The helper does not wire into shared provider code, mute the mic, cancel server generation or stop backend actions. Pending queued audio is bounded, not total server output. Preserve the rest of the provider's WS input/output flow control and independently gate stale callbacks by session/epoch. No paid or device calls were used in these tests.
