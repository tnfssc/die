# Live capability denials: connected provider probe (2026-09-25)

## Actual selection and method

`loadLiveConfig()` selected **openai / gpt-realtime-2.1** (including openaiModel gpt-realtime-2.1); `createDefaultLiveCredentialService(undefined, 'openai')` reported `stored_api_key` and resolved the key. No ambient key fallback, secret output or credential edit. Provider WebSocket `/v1/realtime?model=gpt-realtime-2.1` accepted session.update in all 34 trials; no provider errors. A separate direct model probe uses **text input** and the production audio-output configuration, but does not play output. Each request had its own session and 20-second deadline. No microphone, speaker or private desktop file was used.

Run `bun install --frozen-lockfile --ignore-scripts; bun scripts/prepare-assets.ts; DIE_CAPABILITY_PROBE=1 bun scripts/probe-live-capability.ts --disclose-root baseline:jobs grounding:jobs baseline:audio grounding:audio` (explicitly paid; --disclose-root consents to sending generated root, possibly local paths, to the configured provider; output may echo it). The script loads the selected provider/model and credential using app resolution. It obtains the execute-only tool and root via `createPromptPreview({rootMode:'orchestrator'})` for rounds 3–4: Pi/Die production prompt assembly in a new isolated synthetic session. This is closer to the ordinary effective root than a hand-written approximation, but excludes the active user's project overrides, session history, Live acquisition and real runtime tool dispatch. Rounds 1–2 used reconstructed Die base + working values and, in round 1, an abbreviated execute description; treat them as exploratory only. Round 2 used the production execute description/schema; rounds 3–4 used the exact offline preview execute declaration. The isolated preview uses a fresh temporary cwd each run, so hashes change between invocations.

Variants append to the **same root**, never replace it: baseline (no addition), grounding (one short assertion that execute remains available in voice, host helpers are inside execute, action first and truth about actual results), intent (grounding plus correction-after-refusal/action intent), description (grounding and alternative clearer execute description). The description variant was only tested in the exploratory reconstructed-root round. Synthetic scenarios: jobs list, file read of nonexistent `/probe/sandbox/note.txt`, audio cleanup of nonexistent `/probe/sandbox/clip.wav` (explicit worker request and natural request), weather lookup, and correction after an *injected assistant refusal* in rounds 3–4. The synthetic tool returns an empty jobs list, sentinel file text, no configured weather data, or explicit fake audio acceptance/interception. **The probe never evaluates model-generated code, performs a real read, starts a worker, runs a shell, checks the weather or processes audio.** Tool call choice means the model requested `execute`, not that the host performed it. Model-supplied code and spoken transcript are in [evidence](capability-probe-evidence-2026-09-25.jsonl), 34 trials.

## Observations

- 34/34 trials chose execute at least once; jobs and file cases, explicit and natural, called jobs.list / filesystem APIs in both baseline and grounding. In the offline production-root set (rounds 3–4, 14 trials), 14/14 called execute. The preseeded refusal was corrected in both baseline and intent: each actually *chose* a file-read call (mocked) and said the earlier denial was wrong. This is not a reproduced spontaneous false denial; no real voice input or long conversation was tested.
- Audio with an **explicit request to delegate**: reconstructed-root round 1 baseline and grounding both called subagent. With production execute description in round 2, baseline instead attempted a direct ffmpeg command; grounding and description variant chose subagent. With offline preview root in round 3, baseline and grounding both chose subagent. On the natural audio request in round 4, baseline chose direct command and grounding chose direct command first, then subagent after mock interception. The single grounding sentence is not sufficient to guarantee immediate worker delegation for natural audio. Never infer real audio cleanup from these calls.
- Weather baseline and grounding (round 2, one each) both chose execute/fetch and correctly reported inability to verify current weather from the mocked failed result. Neither performed a real network lookup; one reply suggested sharing a weather API key, which is unnecessary for many public weather sources.
- Responses to fake audio acceptance were mixed: several accurately noted no audio was processed; some also called the synthetic worker a running job and invited further action. This is a mock-result wording issue, **not proof of an active job**. In a natural-audio direct-command interception one answer incorrectly inferred the file location was restricted and requested an upload. Tool-result accuracy is a separate concern from deciding to call a tool.

**Interpretation:** This bounded, text-input connected probe did not reproduce capability denial. Baseline often used the tool correctly, including correction after a seeded denial. Do not claim the grounding prompt fixes spontaneous denials or ship it based on these samples. The parent observation of real mic/voice turns falsely denying capability remains unexplained: potential factors include speech/transcription, longer context after tool responses, active root/project differences, and timing. Next test should compare the *actual acquired Live root and user-turn transcript* under a controlled voice session or recorded ASR fixture, with safe mocked execute and multiple turns. Preserve the main-owner tool boundary; do not introduce a companion persona or alternate executor.

Values unchanged: the existing “go look”, “show what is real”, and “leave user's work safe” cover the observations. No production prompt change recommended yet.
