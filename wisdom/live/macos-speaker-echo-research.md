# Hands-free MacBook speaker echo: research, not an acoustic pass (2026-09-24)

**Decision:** Keep the existing single `AVAudioEngine` full-duplex Apple voice-processing path for a consented, instrumented **built-in Mac mic + built-in speaker** trial. It is the simplest plausible native AEC path; `isVoiceProcessingEnabled == true` and the user's v0.8.2 startup success prove neither suppression nor uninterrupted listening. Do not ship a speaker-quality claim, change runtime, add WebRTC, or mute the microphone during playback on this evidence. Headphones remain a useful control, **not** the requested solution.

## Observed sources and graph

- [Apple WWDC19 AVAudioEngine session](https://developer.apple.com/videos/play/wwdc19/510/) says setting voice processing on either input or output I/O node enables the mode and requires a stopped engine when changing it. [Apple WWDC23 voice processing](https://developer.apple.com/videos/play/wwdc2023/10235/) describes Apple's processing as AEC, noise suppression and automatic gain control, tuned for product/device routes, with other-audio ducking controls. [API availability](https://developer.apple.com/documentation/avfaudio/avaudioionode/setvoiceprocessingenabled(_:)) is macOS **10.15+**; newer ducking controls in [LiveKit's wrapper](https://github.com/livekit/client-sdk-swift/blob/main/Sources/LiveKit/Audio/Manager/AudioManager.swift) are gated macOS 14+. Do not infer the newer controls exist on older OSes.
- Apple's actual [Using voice processing sample](https://developer.apple.com/documentation/avfaudio/using-voice-processing) [downloaded source ZIP](https://docs-assets.developer.apple.com/published/8599a413511b/UsingVoiceProcessing.zip), `AVEchoTouch/AudioEngine.swift` lines 94–125, calls `input.setVoiceProcessingEnabled(true)` before wiring file players -> `mainMixer` -> `output`, and installs an input tap; lines 178–180 expose bypass for comparisons. This current sample's published target is **iOS 17+ / Catalyst 17+**, not proof of MacBook speaker performance. Older third-party [stripped AVEchoTouch derivative](https://github.com/cstarkjp/AudioEngineDemo/blob/master/AudioEngineDemo/AudioEngine.swift) instead targets iOS 12 and **removes iOS 13 voice processing**; not evidence for enabled AEC.
- At local source commit `7db8b85721d103ebd770c43d4aaae35de1a9255c`, [native/live-lab/main.swift](../../native/live-lab/main.swift) lines 157–210 enables processing on the input before reading **post-enable** I/O formats; mono Float32 source node feeds the main mixer -> output node using actual output format, input tap on the same engine feeds ring -> converter -> 16 kHz PCM16 capture; source renders 24 kHz PCM16 at device rate. This matches Apple's important same-engine render/capture topology; no explicit far-end PCM reference needs to be sent to Apple's voice-processing I/O in this graph. **Inference**, not an Apple guarantee for every route: playback through this engine's output is available to its voice-processing implementation. An unrelated player/output or split devices would need separate validation; feeding raw PCM to an unrelated AEC is not equivalent.
- [AudioCore.c](../../native/live-lab/AudioCore.c), [helper README](../../native/live-lab/README.md), and [live-lab audio controller](live-lab-audio-controller.md): output interpolation is linear (quality/latency to measure); capture converter handles device-rate -> 16 kHz; 20 ms emitted frames, 10 ms drain timer, ~1 s bounded playback queue, `played queuedMs=0` has 200 ms reporting grace, **not** proof of actual speaker silence. Route configuration change currently stops the helper (`route_lost`); restart and retest instead of assuming continuity. Startup runs on default devices; permission/TCC, device selection and real output are not CI-tested. v0.8.2 user's startup success is a startup observation only.

## Processing boundaries and tradeoffs

- Apple processing is voice-oriented: AEC removes **far-end loudspeaker sound re-entering mic**, NS reduces environmental noise, AGC adjusts mic gain. All may alter timbre/music. NS alone is **not** AEC, and AEC won't suppress a real near-end speaker indiscriminately. Test end-of-playback reverberation/tail and double-talk, not just quiet-room echo. Don't assume any hard latency or echo-reduction number without capture on the target machine.
- The source does **not** configure separate voice-processing ducking or AGC/bypass modes. Apple's `AVAudioVoiceProcessingOtherAudioDuckingConfiguration` concerns **other audio** ducking, not a replacement for echo cancellation or a reason to duck/mute our own reply. Avoid adding ducking until an observed competing-audio problem. Distinguish Mac system volume, application PCM gain, and microphone AGC in tests.
- Built-in mic+speaker, wired headset, Bluetooth headset/HFP and Bluetooth A2DP/airplay/external/split output are different acoustic/clock/latency paths. In particular Bluetooth input/output may switch profile/rates and route, high latency or separate devices can defeat assumptions. **Hypothesis requiring route tests**, not a categorical Apple guarantee. Constrain first acceptance to built-in route, log input/output names, rates and failures; later opt into other routes individually. [Apple's echo-cancelled-input API](https://developer.apple.com/documentation/avfaudio/avaudiosession/setprefersechocancelledinput(_:)) notes voice-processing APIs already apply echo cancellation to supported routes (iOS AVAudioSession API, not a Mac graph patch).
- **Never default to mic mute during assistant playback.** It hides echoed speech by also hiding the user's simultaneous speech; no voice barge-in/interruption can reach the model. Leave capture on during playback, flush *outgoing* audio only on actual interruption, preserve normal utterance tails, and assess false interrupts separately from true double-talk. If short turn-end/hardware tails trigger false interruption, investigate capture-vs-render alignment, AEC route and interruption threshold after measurement; a grace/holdoff may itself lose legitimate barge-in. Existing synthetic queue tests validate flushing, not acoustic cancellation.

## Other implementations (alternatives only if measured Apple path fails)

- [LiveKit Swift SDK AudioManager](https://github.com/livekit/client-sdk-swift/blob/d6765cc9f7cbee78a993718915a1e9fdc72983ea/Sources/LiveKit/Audio/Manager/AudioManager.swift) (source tree commit `d6765cc9f7cbee78a993718915a1e9fdc72983ea`): supports Apple platform processing with bypass/AGC state and selectable WebRTC **software** processing when platform processing disallowed; this is a full WebRTC device/processing stack, not a switch to add to our helper. A software AEC must receive correctly timed reverse/render audio and capture at supported framing/rates ([LiveKit Python APM reverse-stream documentation](https://docs.livekit.io/reference/python/v1/livekit/rtc/apm.html)). Only consider a tightly scoped software APM trial if route-constrained built-in speaker measurements fail and reference/timing can be furnished; avoid stacking software AEC on Apple AEC (double-processing).
- [Pipecat's SmallWebRTC transport](https://github.com/pipecat-ai/pipecat/tree/9d4c5087aaa1bd5193262136a59d677348bb950c/src/pipecat/transports/smallwebrtc) at commit `9d4c5087aaa1bd5193262136a59d677348bb950c` is a network transport; its Python audio-filter interface is not a native macOS built-in mic/speaker render-reference solution. Browser WebRTC can be another architecture, with device-routing/runtime cost; not justified before native measurement.

## Consent-based staged acceptance (no run performed here)

1. User on actual Mac with explicit permission, no paid API required: log macOS/model, exact built-in input/output, physical/system/app volume, input/output rates and format, helper errors, time-aligned rendered PCM and post-processed capture **locally** (private speech, opt-in storage/deletion). Never auto-open devices. Check capture-only and output-only, route changes, stable latency, clipping/dropped frames. Baseline with voice processing enabled; optional explicit disabled/bypassed **diagnostic run** only on same equipment if safe to do so.
2. **Echo-only**: play a known speech/test phrase at low, normal and high safe volumes while user silent. Measure correlation/delay, returned speech recognizability and echo return loss relative to bypass/control, including after render queue drains. Real speaker acoustic tail matters; provider transcript/false interruption should not contain the played phrase. Compare headset control but pass criterion is built-in speakers.
3. **Double-talk**: user speaks over early/middle/end of playback at normal and quiet levels; user words must be capturable/recognizable promptly, actual interruption stops playback without losing user's words; measure user-speech onset -> stop, false interruptions on echo-only, missed interruptions, and recovery. No default input mute/gating.
4. **Far-end tails/long replies**: play multiple seconds with distinctive final words; ensure actual output audible through the last word, capture echo/tail after queue reports zero, no early flush or repeated self-trigger. Repeat for volume steps, quiet/noisy room, Mac lid/distance, and after device/route change (restart if needed). Distinguish server VAD errors, playback truncation, and acoustic echo with timeline; don't claim quantitative pass until a user-defined barge-in latency/echo/false-trigger threshold is recorded. Bluetooth/external tests are separate scope.

**Evidence limits:** This Linux-side source/documentation review used `tvly search` for Apple, LiveKit and WebRTC and fetched Apple ZIP / public upstream source; no physical speaker/mic, Mac runtime, paid API, credential, or acoustic samples. Values unchanged: existing evidence-before-claim and user-platform validation lessons in [values](../values.md) already cover this case.

## Native follow-up (no acoustic measurement)

The helper explicitly clears and verifies the Apple input I/O node voice-processing bypass flag, checks that input processing remains enabled and unbypassed after starting, and includes capture/render sample rates and these processing flags in its `ready` event. This is a configuration self-check, **not** measured AEC. Apple [AVAudioInputNode.isVoiceProcessingBypassed](https://developer.apple.com/documentation/avfaudio/avaudioinputnode/isvoiceprocessingbypassed) documents this as bypassing microphone uplink processing (macOS 10.15+ in Apple documentation JSON). AVEchoTouch `AudioEngine.swift` sets `input.isVoiceProcessingBypassed` for its diagnostic bypass comparison; the same sample enables processing before connecting players to the mixer and tapping capture. The pre-existing helper already uses this single-engine graph, post-enable formats, and full-duplex capture; no second AEC or ducking mode was justified. No AGC override was added: WWDC23 describes integrated voice processing, and turning off AGC without a device-specific observed issue risks quieter user speech. The bypass check requires Mac CI compile/real route confirmation. On route change the helper still stops; restart and observe new `ready` rates. No physical Mac mic/speaker, credentials, or audio recording was used here.

Manual short opt-in test at normal safe built-in speaker volume: start the helper from an interactive Mac terminal with permission, confirm `ready` reports enabled=true, bypassed=false and plausible rates. Play a short known speech clip through the helper while silent, then record processed capture locally **only with explicit consent**; check for audible/recognizable echo including after the clip ends. Speak different words over the middle of another clip; ensure they survive promptly in captured audio, not merely that echo disappears. Repeat once with headset as control and after restarting on route changes. Delete recordings after inspection. For provider interruption acceptance repeat with the live session, comparing echo-only false interruptions against true barge-in latency. A source-level check cannot establish either result.
