## Implementer recommendation now

* For a **server-owned mic/speaker** Realtime conversation use the GA Realtime WebSocket API, not GPT-Live's different `/v1/live` protocol and not the legacy preview schema. Current official WebSocket guide explicitly connects `wss://api.openai.com/v1/realtime?model=gpt-realtime-2.1` with `Authorization: Bearer <OPENAI_API_KEY>` on the server. Use `gpt-realtime-2.1` as the documented latest mainline Realtime ID; `gpt-realtime-2.1-mini` is the cheaper sibling. The official changelog lists **Jul 6, 2026** (under July 2026) release of both for `v1/realtime`, with 2.1 improvements to alphanumeric recognition, silence/noise and interruption. Model catalog lists 2.1 before 2, 1.5; the 2.1 model page describes configurable reasoning/tool use. No date-stamped 2.1 snapshot ID is listed on that page: **July 6 is release-date evidence, not part of the model ID**. Do not use `gpt-4o-realtime-preview` or assume older `gpt-realtime` is newest. [Changelog](https://developers.openai.com/api/docs/changelog), [models](https://developers.openai.com/api/docs/models), [2.1](https://developers.openai.com/api/docs/models/gpt-realtime-2.1), [WebSockets](https://developers.openai.com/api/docs/guides/voice-websockets).
* Wait for `session.created`, send `session.update` with `session: {type:'realtime', model:'gpt-realtime-2.1', output_modalities:['audio'], audio:{input:{format:{type:'audio/pcm',rate:24000},turn_detection:{type:'server_vad',create_response:true,interrupt_response:true},transcription:{model:<supported ASR model>}},output:{format:{type:'audio/pcm'},voice:'marin'}}, instructions, tools:[...] }` (choose a supported ASR model from the current session reference; this placeholder is not a literal API value). Official guide shows this nesting and `session.created`/`session.update`; server VAD docs place `create_response` and `interrupt_response` **inside** `audio.input.turn_detection`. Output modality `audio` includes audio-associated transcript events; do not assume separate `['audio','text']` is required. For audio input append base64 PCM16 24 kHz with `input_audio_buffer.append` continuously; VAD commits/creates responses automatically. Do not repeatedly manually commit/create on VAD-managed turns. Verify actual transcription model/config against current reference before coding. [Conversations](https://developers.openai.com/api/docs/guides/realtime-conversations), [VAD](https://developers.openai.com/api/docs/guides/realtime-vad), [transcription](https://developers.openai.com/api/docs/guides/realtime-transcription).
* On `input_audio_buffer.speech_started`, **immediately flush local queued/scheduled output**. With VAD `interrupt_response:true`, server automatically cancels in-flight generation; do not blindly send duplicate `response.cancel`. For explicit/manual cancellation, `response.cancel` stops generation, **not** client-owned speaker audio. Send `conversation.item.truncate` with assistant audio `item_id`, `content_index`, and `audio_end_ms` measured from **actual played samples** for that item (PCM16 24 kHz => 24 frames/ms), not received/queued bytes or wall time. Account for helper's best available played-frame estimate and distinguish estimated drain from physical confirmation; reset counters per item/epoch. Docs say WebRTC/SIP truncate automatically, WebSocket client must stop and truncate; truncation removes unplayed transcript but does not synthesize a precisely aligned partial transcript. Avoid truncating if no valid audio item; avoid exposing unplayed assistant transcript as heard speech. [Interruption/truncation](https://developers.openai.com/api/docs/guides/realtime-conversations#interruption-and-truncation), [truncate event](https://developers.openai.com/api/docs/api-reference/realtime-client-events/conversation/item/truncate), [cancel event](https://developers.openai.com/api/docs/api-reference/realtime-client-events/response/cancel).
* Tools: session `tools` functions with name/description/JSON schema, `tool_choice:'auto'`; assemble arguments by `call_id`/item (or use completed `response.done.response.output` function-call items), run only approved host tools, return `conversation.item.create` with `item:{type:'function_call_output',call_id,output:<string>}`, then `response.create` to continue. Tool-call completion is **not** user-facing task completion; sanitize tool results/errors and preserve existing host permission boundary. [Function calling](https://developers.openai.com/api/docs/guides/realtime-conversations#function-calling).
* Transcript: correlate `conversation.item.input_audio_transcription.*` via `item_id`/`content_index`, finalize with `.completed`; official transcription guide explicitly says completion events **from different speech turns are not guaranteed in order**. Preserve conversation order by item metadata, not event arrival; separate tentative deltas from final text. Assistant `response.output_audio_transcript.delta/done` is distinct from `response.output_text.delta/done`; tie to response/item/content and interruption state. Do not claim ASR is a verbatim record of model-heard audio or queued output is heard speech. [Transcription](https://developers.openai.com/api/docs/guides/realtime-transcription), [events in conversations](https://developers.openai.com/api/docs/guides/realtime-conversations).
* Auth: an OpenAI **Platform API key** is the server-side Realtime bearer credential; do not reuse or inspect Codex's ChatGPT sign-in/OAuth cache, and do not expose the key to browser, transcripts, tool logs or error output. Codex docs describe browser-based ChatGPT sign-in as a Codex login path **separate** from API-key sign-in and explicitly say API-key usage is billed through Platform at standard API rates. No official evidence found that Codex OAuth is a supported bearer for Realtime. If no configured Platform key, fail closed with clear setup instructions. [WebSocket auth](https://developers.openai.com/api/docs/guides/voice-websockets#connect-via-websocket), [Codex authentication](https://developers.openai.com/codex/auth).

## GA vs preview and SDK/sample caveats

GA examples use `session.type:'realtime'`, `output_modalities`, nested `audio.input/output`, `response.output_audio.delta`, `response.output_audio_transcript.delta`. Older preview snippets use flattened `input_audio_format`/`output_audio_format`, `modalities`, `response.audio.delta`, `response.audio_transcript.delta` and sometimes `OpenAI-Beta: realtime=v1`; do **not** mix event names/fields. Official [openai-node Realtime docs](https://github.com/openai/openai-node/blob/main/docs/realtime.md) document `OpenAIRealtimeWS` (Node ws) and `OpenAIRealtimeWebSocket` (web WebSocket) and `response.done` statuses incl. failed/cancelled/incomplete. Official [websocket.ts sample](https://github.com/openai/openai-node/blob/main/examples/realtime/websocket.ts) shows `OpenAIRealtimeWebSocket({model:'gpt-realtime'})`, open listener, GA `session.update:{type:'realtime',output_modalities:['text']}`, text item/create, response.create; **sample pins older alias and is text-only**, not proof of 2.1 audio config or playback semantics. Use current guide/model docs for model ID and voice shape. [Old preview model page](https://developers.openai.com/api/docs/models/gpt-4o-realtime-preview), [GA model page](https://developers.openai.com/api/docs/models/gpt-realtime), [current guide](https://developers.openai.com/api/docs/guides/realtime-conversations).

## Conversation-window retention (separate from barge-in truncation)

Follow-up tvly search with official-reference excerpts on 2026-09-24: the official [Realtime client events reference](https://developers.openai.com/api/reference/resources/realtime/client-events), [developer notes](https://developers.openai.com/blog/realtime-api), and [Prompt Caching 201 sample](https://developers.openai.com/cookbook/examples/prompt_caching_201) document default `truncation: "auto"`: oldest messages are removed to fit the model input window. `"disabled"` errors rather than pruning; the retention-ratio form can drop more history per truncation for better cache reuse (e.g. 0.8 retains 80% of the allowed post-instruction conversation tokens). This candidate leaves the server default intact, rather than copying a token-window size from an older model or introducing a cache-tuning setting. Local received transcript history/snapshots remain separate: retaining those does not prove that the provider still has every earlier turn in its active context. Item audio truncation on interruption is a different operation and is still client-owned over WebSocket.
