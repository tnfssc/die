No native error code, timing within handshake/provider/start, TCC status, device details, or crash log was provided. Do not infer a cause from that text: extension.ts previously discarded the helper callback code. The released Mac arm64 binary embeds the helper (SHA256 71092e078150d443bc0d2761813decfa76bb15ad2002e738b32c78f32f99717b), and release CI proved device-free --self-test and hello/stop only. Physical mic/speaker, permission prompt, signed executable TCC identity and provider sessions were not tested. Helper is extracted into a fresh private temporary directory each launch (helper.ts), executable chmod 0700, and is not signed/notarized. The helper has an embedded NSMicrophoneUsageDescription, but TCC attribution for unsigned extracted executables versus Terminal/die remains unknown on user's machine. Do not advise blindly resetting TCC or enabling access without consent.

The native helper has distinct permission rejection, voice processing, input/output format and engine-start branches; the latter previously all became audio_start. Format guard built AVAudioFormat before checking mixer sample rate; reordered guard so invalid/out-of-range rates are rejected before construction. The startup catch previously called removeTap even on failures before installTap; now removes only an installed tap. Neither failure is proven to explain this user report. No proof that this was the user's failure. Swift builds and AVFoundation behavior must be checked on Mac CI; Linux cannot compile it. Native diagnostic phase codes and UI allowlist now identify known stages without forwarding messages, stderr, process paths or provider secrets. Unknown codes remain unclassified. If helper dies before sending an error, only a generic launch/process diagnostic can be given, not a claimed TCC cause.

Diagnostic sequence for consenting Mac user: run `die --live-lab-self-test` (no devices or provider), then `/live-lab mic-check` in a local interactive session. Mic check requires explicit UI confirmation, starts native input/output briefly, discards every captured buffer, does not call credential service, provider, playback, or persist audio. macOS might show a permission prompt; if denied, inspect System Settings → Privacy & Security → Microphone for launching terminal/die. Report the bounded code and step, no API keys or raw logs. A successful route-ready only establishes device startup, not actual audible playback, microphone signal quality, echo cancellation, or provider auth.
