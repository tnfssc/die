# Stable v0.9.0 Mac speaker self-interruption: source audit (2026-09-24)

**Finding:** Headphones work; the user reports immediate self-interruption on built-in speakers. This is a real end-to-end failure, **not a source-proven AEC defect**. The code contains no local speech detector, echo gate, or automatic mic mute. Most likely *hypothesis*: rendered reply leaks into uplink despite requested Apple voice processing; Gemini automatic activity detection treats it as a new user turn and reports an interruption. Other unexcluded causes include device/route mismatch, voice processing not effective on that route, acoustic tails, and server activity sensitivity. The source cannot distinguish them without consented capture and event timing. No runtime behavior changed in this audit.

## Trace, with source and commit evidence

- Native graph: `0bebcd22` added explicit unbypass + post-start checks/ready flags; earlier `519e6ce` wired output graph. `native/live-lab/main.swift:157-207` creates **one** engine, enables voice processing on input before fetching post-enable formats (169-181), creates a 24 kHz PCM16 -> device-rate mono Float32 source (182-189), connects source -> main mixer -> output I/O (190-195), and taps **inputNode output bus 0**, using post-enable output format (196-207). It copies `buffer.floatChannelData?[0]` in <=1024-frame slices into the capture ring: only first channel, neither a mixer/output tap nor a manually reconstructed raw-device capture. A first-channel extraction is proven; whether it is **actually AEC-processed on this Mac/route** is not measured by source. Input-node output-tap placement and enabled/unbypassed state make processed uplink the intended Apple graph, not proof of acoustic suppression. If multichannel input is presented, other channels are discarded; no evidence that this explains the speaker-only symptom. Apple [WWDC19](https://developer.apple.com/videos/play/wwdc19/510/), [WWDC23](https://developer.apple.com/videos/play/wwdc2023/10235/), and the [AVEchoTouch sample](https://developer.apple.com/documentation/avfaudio/using-voice-processing) support enable-before-wiring, same-engine playback/tap and voice-processing AEC; see [prior research](macos-speaker-echo-research.md). Current documentation was not independently fetched in this audit (tvly unavailable here).
- `native/live-lab/main.swift:7-52,208-280` converts first-channel Float32 device-rate capture to 16 kHz mono PCM16 in 20 ms packets, drains every 10 ms, and keeps capture active while playing; configuration change stops the engine and needs restart. Ready contains enabled/bypassed/rates (213-225), but `src/live-lab/audio.ts:240-253` accepts any `ready` without inspecting those fields: native checks currently guard state, not effective AEC. `AudioCore.c:89-104` bounds capture and counts dropped frames. `src/live-lab/extension.ts:222-228` forwards all capture to the voice session, even during playback.
- Playback: `src/live-lab/session.ts:343-390` accepts Gemini model PCM 24 kHz and emits it with playback epoch; `extension.ts:75-95,167-187,254-268` hands it to the scheduler and flushes on server `serverContent.interrupted` only. `src/live-lab/playback.ts:64-113,154-229` copies/bounds chunks, sends 20 ms frames with pacing and shallow ~20–80 ms native ring, passes short normal-turn tail without flush, drops old pending chunks on interruption and flushes native generation before new sends. `src/live-lab/audio.ts:310-335,351-378` sends play/flush over helper stdin; write completion means accepted to pipe, not audible. `native/live-lab/main.swift:282-307` admits generation-tagged PCM; `AudioCore.c:18-86` renders interpolated mono into the same engine source callback, generation flush drops old audio. Queued sample count is decremented when read for render, **not at acoustic output**; helper's 200 ms reported-zero grace (main.swift:229-239) is an approximate UI aid, not an AEC or physical-tail barrier.
- Server: `src/live-lab/session.ts:112-145,179-201` uses `realtimeInputConfig.automaticActivityDetection.disabled=false`, continuously `sendRealtimeInput({audio:{data,mimeType:'audio/pcm;rate=16000'}})` and no playback-scoped VAD disable. `serverContent.interrupted` at 348-355 is an **incoming provider notification**, not a local threshold decision; it increments epoch, notifies extension, skips same-message stale audio. Turn-complete at 386-390 is distinct and does not flush. `extension.ts:178-187` only clears playback, and `session.ts:322-339` explicitly leaves jobs running. Provider setup precedes audio start (extension.ts:218-312); do not change these lifecycle properties to hide echo.

## Narrow next action, not a speculative patch

1. On a consented built-in Mac mic/speaker run, verify ready processing flags/rates **and device route**, without treating flags as AEC validation. Play distinct known far-end speech with user silent; capture the processed uplink locally only with explicit consent and time-align to emitted PCM, checking echo recognizability/level and late tail. Log monotonic timestamps for render enqueue/callback, capture chunks, server interruption, flush and reported queue; distinguish a provider cancellation from local audio error. Repeat on headphones control and after route restart. No credentials/audio in bug reports; delete captures after review.
2. Repeat with real overlapping user speech, especially at first playback onset and after final render: it must pass and interrupt promptly. Compare echo-only false interrupts vs true barge-in before tuning server activity thresholds or adding any holdoff. Avoid muting/gating the mic (destroys full duplex), force-flushing normal turn tails, or stopping agent jobs. If processed capture clearly contains echoed speech, first isolate Apple's processing/route and render reference using a bypass comparison **only as an opt-in diagnostic**; consider alternative AEC only on measured failure. If capture is clean yet server interrupts, inspect provider events and VAD behavior before changing the graph.
3. Add a Mac-only, opt-in synthetic render/capture timing + real-speaker acceptance test; existing queue/flush unit tests cannot test AEC. This Linux audit ran `clang -std=c11 -Wall -Wextra -Werror -fsanitize=address,undefined native/live-lab/AudioCore.c native/live-lab/test-core.c -o /tmp/live-lab-audit-test && /tmp/live-lab-audit-test` (passed). Swift/macOS and Bun tests were not run: no Mac device, Bun missing and untrusted mise configuration; no trust/config changes made. No physical audio, credentials or provider request used.
