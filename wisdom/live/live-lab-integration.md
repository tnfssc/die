# Voice-only /live-lab phase-one integration

This is an opt-in *separate* command. /live remains unchanged. /live-lab status and opening the menu do not resolve auth, start the provider, spawn the helper, or open devices. /live-lab start asks consent for paid Google audio and microphone/speaker use before any work. No coding-agent bridge, tools, chat messages, persisted transcript or agent cancellation. /live-lab stop shuts down the voice run, not agent work. Only local interactive macOS/Linux TUI is allowed (not SSH/web/child agents). Voice uses gemini-3.8-live, not the coding model.

Session connect must finish its SDK setup acceptance before helper.start opens devices. Helper.launch awaits protocol-v1 hello without opening the mic. Each run owns its AbortController and lifecycle epoch; late helper launches are closed, and late provider connections are closed by VoiceSession. Errors shown are static, not raw SDK/helper errors. Auth comes from the existing safe ModelRuntime Google API-key service; OAuth is not silently used, and live.env is not consulted except explicit legacy import elsewhere. No real key/device/network was used by extension tests.

The widget displays only recent sanitized input/output transcripts (last 8 lines, 180 chars per line), never writes them to chat or diagnostics. Stopping removes widget and status. Diagnostics are metadata only: frame counts, output duration, turn count, helper queuedMs and bounded pending ms. SDK audio packets split to <=9600 bytes (200ms PCM16 24k); serialized helper writes avoid its 64KiB stdin queue limit. Pending memory capped at 96000 bytes (2 seconds, max single SDK packet). If the provider outpaces playback or helper reports >1200ms queued, the voice run stops visibly rather than quietly dropping speech. The SDK interruption epoch clears unsent playback and issues helper generation flush. Ordinary turnComplete does NOT flush tail. played(queuedMs) is actual helper queue telemetry, not proof of audible playback after a successful stdin write. Continuous 20ms microphone chunks go to SDK during playback; no default push-to-talk.

Native targets: macOS dist/live-lab-audio, Linux dist/live-lab-audio-linux. Audio controller must select platform-specific trusted path anchored at module/package location, never current directory; Linux platform guard needs to allow local TUI Linux. Helper override is for trusted developer paths only. Native work belongs to Mac/Linux helper owners; integrate their build scripts and verify their protocols before making a candidate. The Mac helper uses platform frameworks and must be built on a Mac runner. Linux helper uses PulseAudio and WebRTC processing and currently needs native development libraries; downloadable Linux candidate must bundle/resolve runtime dependencies honestly. No stable release or tag for this lab; a manual Mac/Linux helper build smoke and isolated phase-one candidate are appropriate once native scripts align, not automatic stable release packaging. The existing single Bun executable cannot itself provide the native helper; a real downloadable candidate needs a matching executable sidecar, executable mode, architecture checks and checksums, or a verified installer path. No user brew/Xcode prerequisite should be asserted until CI-built Mac artifacts are proved.

Synthetic tests exercise start/stop races, decline, full duplex, bounded frame split, transcript sanitization, interruption vs turnComplete, failure cleanup and local gate. They do not prove acoustic echo suppression, device routing, latency, provider quality, billing, or physical Linux/macOS operation. Parent must test actual helper handshake, real local mic/speaker loopback, barge-in and playback drain on each platform with explicit consent before calling baseline accepted.
