# Public provider docs: browser Live authority boundary (2026-09-25)

Scope: read-only, unauthenticated public documentation fetched live on 2026-09-25; no keys, paid calls, protocol acceptance tests, or edits to foundation files. URLs below are canonical pages actually fetched (OpenAI legacy `platform.openai.com/docs/guides/realtime-webrtc` and `.../realtime-server-controls` redirected to the developers.openai.com pages). Quotes are short excerpts; protocol behavior beyond the published examples is marked as inference.

## Decision / immediate blocker

**Do not treat a directly connected browser as a trusted author of instructions, tool results, user transcript, or approvals.** Gemini ephemeral tokens protect the long-lived API key and can pin connection configuration, but deliberately allow the browser to send Live content/tool responses; no Gemini sideband analogous to OpenAI's is established by these docs. OpenAI WebRTC + a server-authenticated sideband is a viable **media transport + server-side tool-execution topology**, not a provider-enforced browser read-only session: the browser data channel can send session and conversation events, while the sideband shares that session. Keep all application tool execution, authorization, durable transcript, and approval state on the backend. Accept a provider model tool request only as a *proposal* and independently check policy/user identity/argument provenance; accept tool completion only from the backend's own invocation/result ledger, not a browser-visible session event. If the requirement is that browser code cannot mutate the provider session or inject purported user content, neither directly connected design is sufficient on the published evidence; relay/control the relevant channel server-side, or choose a different trust model. Do not equate a model response or sideband observation with proof of spoken user approval.

**Nuance:** This is a capability/security-boundary conclusion, **not** a demonstrated exploit against a provider. Docs show event shapes and shared-session wiring, not which conflicting sideband/browser event wins, whether an arbitrary forged `function_call_output` is accepted for an unknown call ID, whether provider rejects a specific session field, or whether the sideband can distinguish event origin. Provider-generated function-call IDs/events should not be called browser-forged without testing; a real model request can still be induced with untrusted content. A server can prevent application-side tool execution even when the model session is polluted.

## Gemini: ephemeral browser websocket, formats and authority

- [Ephemeral tokens](https://ai.google.dev/gemini-api/docs/live-api/ephemeral-tokens): `Your backend sends the token to the client for WebSocket connections to Live API.` `The client then uses the token as if it were an API key.` Google warns `ephemeral tokens can be extracted from client-side applications such as web browsers or mobile apps` and says `It's also possible to lock an ephemeral token to a set of configurations` (example `liveConnectConstraints` pins model and configuration). These limits reduce key exposure/setup tampering; they do not make client-sent content trustworthy. Defaults on that page: one minute to start a new session, 30 minutes to send messages over the connection; `uses: 1` and resumption caveat below. Tokens are Live API/v1beta only; not general Gemini API credentials.
- [Live API capabilities](https://ai.google.dev/gemini-api/docs/live-api/capabilities): model comparison says `send_client_content is supported throughout the entire session lifecycle with explicit roles (user or model).` This is a concrete browser-origin content / purported transcript mutation surface; model-role content must not be interpreted as backend-authored. Same page: `Audio data in the Live API is always raw, little-endian, 16-bit PCM. Audio output always uses a sample rate of 24kHz.` It says input is natively 16kHz and other rates can be resampled with `audio/pcm;rate=16000` MIME sample-rate label. Audio/transcription events are distinct from authenticated approvals. No documented Gemini Live WebRTC transport on these pages; browser token example is WebSocket.
- [Live API tools](https://ai.google.dev/gemini-api/docs/live-api/tools): the client-side JS example handles `turn.toolCall.functionCalls` then sends `session.sendToolResponse({ functionResponses: functionResponses });`. The example hard-codes a result of `{result: 'ok'}`; the API expects the holder of the session to supply tool results, not to prove that an application server executed the operation. Do not grant authority on the basis of this message alone.
- [Session management](https://ai.google.dev/gemini-api/docs/live-api/session-management): `a session refers to a persistent connection where input and output are streamed continuously over the same connection`. The docs say the connection is limited to around 10 minutes, `SessionResumptionUpdate` supplies a handle for reconnect, and resumption tokens are valid for 2 hours after last termination. The ephemeral-token page explicitly allows resumption within `expireTime` even with `uses: 1`. Expiry/one-use is not a per-message authorization boundary or an immutable conversation.

## OpenAI Realtime: browser WebRTC + trusted sideband

- [WebRTC guide, Realtime section](https://developers.openai.com/api/docs/guides/voice-webrtc?api=realtime) (its [Markdown](https://developers.openai.com/api/docs/guides/voice-webrtc.md) contains both Live and Realtime sections): `To create an ephemeral token to use on the client-side, you will need to build a small server-side application ... using a standard API key ... on your backend server.` It cautions `you only use standard OpenAI API keys on the server, not in the browser.` Browser posts SDP to `https://api.openai.com/v1/realtime/calls` with `Authorization: Bearer ` + ephemeral key, sets remote SDP, uses microphone media tracks and creates `pc.createDataChannel("oai-events")` to send/receive events. Thus WebRTC is not only a passive audio pipe. Server-minted `/realtime/client_secrets` associates a session config; [client-secret reference](https://developers.openai.com/api/reference/resources/realtime/subresources/client_secrets/methods/create) says `Create a Realtime client secret with an associated session configuration` and returns `expires_at`. This is not documentation of field immutability or browser event restrictions.
- [Server-side controls, Realtime sideband section](https://developers.openai.com/api/docs/guides/voice-server-controls?api=realtime): `there are two active connections to the same Realtime session: one from the user's client and one from your application server.` The server connection `can be used to monitor the session, update instructions, and respond to tool calls.` Its WebRTC example reads `Location: /v1/realtime/calls/rtc_123456` from SDP response, then opens `wss://api.openai.com/v1/realtime?call_id=rtc_xxxxx` using the **server's standard API key**. It sends a `session.update` example over that socket. Important integration detail: browser needs to give backend the call ID (or backend must own negotiation), and backend must authenticate/bind that ID to its own user/session; a mere call ID is not authorization to invoke application tools. Sideband keeps business logic/code and API key on server, not browser session contents immutable.
- [Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations): `WebRTC data channel and WebSocket both have .send()` immediately after an example sending `conversation.item.create` with `role: "user"` / `input_audio`. Another example uses `role: "user"` / `input_text`. The page says functions can be configured with `session.tools` in `session.update` **or** `response.tools` in `response.create`; it shows a client event `conversation.item.create` with `type: "function_call_output"`, `call_id`, and `output` JSON, followed by `response.create`. Therefore a backend watching the shared conversation must not assume that a transcript item, config update, or tool-result-shaped item originated on the server side merely because it appeared in provider events. The examples document message shape, **not** successful malicious injection across a sideband, origin-attestation guarantees, or acceptance of a forged call ID. Backend may ignore browser outputs and reconcile against its own call/result ledger.

## Practical split and limitations

Use browser direct transport only when browser-authored user inputs/interruptions are expected and acceptable; pin Gemini setup when using its tokens, and never ship a long-lived OpenAI or Gemini key to browser. For OpenAI, establish sideband before enabling tools; do not assume ordering eliminates races. Keep backend-only declarations/credentials and execution; correlate model call ID to pending backend work, validate arguments and user permission there, and continue from backend-owned results. For a defensible transcript, record backend-observed provider events *with provenance caveat* or relay actual input through a controlled backend path; do not promote client text/audio transcription to verified human speech. Provider ASR is content evidence, not user identity or consent.

Only current public docs were checked; version/availability may change and legacy OpenAI Realtime versus newer OpenAI Live API pages coexist. No paid connection or negative permission test was performed. Specifically unknown: exact provider rejection of concurrent mutations, token/session field locking beyond documented Gemini connection constraints, cryptographic event-origin metadata on a sideband, and behavior of arbitrary invalid function outputs. None of these unknowns justifies treating browser-controlled messages as authoritative.

Wisdom: [values](../values.md) applies especially “One thing, one clear owner,” “Say what proof shows,” and “Show what is real”; no change to values: this is a provider-specific example of existing trust-boundary and evidence principles, not a new cross-project principle.
