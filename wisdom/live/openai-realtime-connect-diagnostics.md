# Realtime connection failure triage (2026-09-24)

Read [values](../values.md), [Realtime research](openai-realtime-research.md), [provider implementation](openai-realtime-provider.md). For stable v0.10.1 reports of connect_failed with gpt-realtime-2.1, do **not** conclude account entitlement from the generic code. New user evidence: the same OpenAI API key succeeds with gpt-live-1. Both implementations pass the same Bearer header via Bun native WebSocket, but GPT-Live connects to /v1/live/sessions and sends session.start while Realtime connects to /v1/realtime?model=gpt-realtime-2.1 and sends session.update. Successful GPT-Live makes a missing key or universal network failure less likely; it does **not** establish Realtime-model access, rule out endpoint-specific network/upgrade handling, or prove that Realtime session setup is accepted. The current [official WebSocket guide](https://developers.openai.com/api/docs/guides/realtime-websocket) still contains the server-side wss://api.openai.com/v1/realtime?model=gpt-realtime-2.1 / Authorization: Bearer example; [official model page](https://developers.openai.com/api/docs/models/gpt-realtime-2.1) still lists the model (checked via unauthenticated docs fetch on 2026-09-24). The guide also mentions the distinct GPT-Live endpoint /v1/live/sessions; this is **not** a reason to switch Realtime protocols. This code uses Bun's native WebSocket with its Bun-specific {headers} constructor option; it does not use the openai-node Realtime SDK. No credentials or provider requests used.

Local Bun 1.4.2 loopback experiment: a server returns HTTP 401 with a private response body/header; native WebSocket emits an error with message "Expected 101 status code" and a subsequent close (1002); neither event exposes HTTP 401. Local 403/429/503 rejected-upgrade tests likewise only establish that the rejection happened, not *why*. Generic previous error/close handlers dropped even that distinction. Do not parse, log or display the raw event message: it contains the request URL and may contain sensitive material. The fix maps only a numeric status if a transport actually supplies one; Bun's otherwise opaque upgrade rejection explicitly says HTTP status unavailable. Server error events during session setup remain separate, using known provider codes or a safe fallback. A raw provider error, response body, URL, header or key never reaches callbacks. The close-after-error path is guarded by single-use serial/closed state so it does not overwrite the initial failure. Socket constructor failures and network failures remain generic without invented HTTP status.

Update for fresh 0.11.0: a provider session error after the upgrade is not an HTTP-upgrade failure; see the [complete session schema audit and safe rejected-field diagnostics](openai-realtime-session-schema-audit.md). Safe provider code/type/param metadata is the next concrete evidence, not an account assumption. Earlier generic failures did not establish a cause; no paid call or device test was made. Offline fake-socket and real loopback handshake regressions plus typecheck are the proof here, not a claim that remote OpenAI accepts this particular key, session configuration or selected model. Existing values on truthful unknowns, privacy, and whole-path verification cover this; values.md unchanged.
