## Audio, asynchronous work, context

- Current src/live/session.ts uses real 16 kHz PCM with automatic detection and AUDIO output/transcription, but its system instruction is src/prompts/live.md and tools are the six narrow declarations in src/live/orchestration.ts: this is a companion delegating to the configured agent, not the main agent. Its sendContext sends non-turn-completing clientContent. Gemini protocol documents text-triggered clientContent and realtime audio (wisdom/live/gemini-live-research.md and official-google-live-tool-examples.md), but this run established neither support by this model for text-plus-execute nor audio VAD-triggered execution. Text success would not establish spoken behavior.
- A delayed simulated response would prove only provider call/result plumbing. Actual async execution needs host-owned execute invocation, bounded pending calls/results, stable call ID matching, truthful background job lifecycle and safe permissions. Preserve live.stop vs jobs.stopWork semantics. Never evaluate generated JS in a probe or create user jobs under probe authority. NON_BLOCKING means concurrency is allowed, not that continued speech/result consumption works. Existing companion caps pending tools at 16, calls at 256 and payloads at 16 KiB; these are not proof of arbitrary normal execute output feasibility.
- Live sessions are finite and stateful; src/live/session.ts currently treats goAway as expiring/close without transparent main-agent continuity. Main-agent adoption needs measured context budget, session resumption/reconstruction, message and job ledger synchronization, token/cost accounting and no side-effect replay. Preview excludes old messages and project context can enlarge the base. No measured model context limit/session expiration or resumption in this investigation. Provider references: https://ai.google.dev/gemini-api/docs/live-api/session-management and https://ai.google.dev/api/live .

## Recommendation / missing acceptance

Keep Pi normal main orchestrator and companion bridge for now. A replacement should route Live to the **same assembled normal system instruction, execute declaration and owned runtime**, not a second privileged evaluator or six-tool façade. Separate voice transport/user-input authority from tool dispatch and preserve normal session/job scope, truncation and cancellation. With an app-configured key, run this bounded probe and check setup acceptance, execute call, model actually consumes ID-matched simulated response (not merely sent), and a follow-up during pending work. Then isolated host-fixture integration should test actual execute code/result and real async lifecycle under normal permissions, text and synthetic audio separately, then full-session continuity/context. None of these provider/host checks passed here.
