# Paired GPT-Live + coding agent: independent architecture review

Read-only review of current source and historical Live notes; no provider/device probe or implementation. User now permits a frontend GPT-Live voice model and selected coding model via client delegation. The old direct-only rejection in main-orchestrator-implementation.md describes the v0.13 direct-owner design, not a present product requirement. Values already cover one owner, honest proof, bounded state and no quiet loss; no values edit.

## Ownership and seam

Keep the ordinary current Pi session/branch and configured coding model as the only coding authority. GPT-Live owns audio, conversational speech and provisional ASR, not Pi tools, job scheduling or permissions. Delegate through the existing SessionHost on that session (src/session/host.ts): delegate(requestId, context) already queues bounded, explicitly provisional context via sendUserMessage with steer and expandPromptTemplates:false, has an ID ledger, branch check, job context and trusted cancellation confirmation. Historical GptLiveDelegationBridge expects submitContextual(requestId, snapshot), which does not exist on this host. Adapt the bridge to host semantics deliberately, preserving offset/revision/uncertainty, rather than casting types or routing through host.send/steer's authoritative latest-user-request template. Host delegate means queued, not executed or done. Never instantiate another Pi coding session.

Direct Live currently acquires main-owner before provider startup and routes typed input, transcripts and execute into Pi itself (src/live/extension.ts, main-owner.ts). Paired GPT-Live cannot acquire that direct-execute owner and run a companion coding turn. Select mutually exclusive runtime paths. Keep the current Pi branch and normal tool declaration/permissions/hooks/results, async JobService and history for the delegated coder; do not let provisional ASR become a final user message or tool arguments. SessionHost.context reads branch user/assistant messages and job state; voice custom entries supplement this. Verify typed text and spoken inputs reach the same coder in order with provenance in history, not an opaque competing log.

## Specific traps

- GptLiveSession has continuous mic PCM, timestamped fragments, client delegation IDs, commentary/thinking and audio. Offset clock and host capture clock are only approximate. Fragments can be corrected, overlap or arrive late: mark omission/uncertainty. GptLiveDelegationBridge fences stale revisions and duplicate IDs, but reconnect must not replay prior work. Pair session-level and host-level ledgers across disconnect/races; never auto-retry uncertain dispatch.
- Host delegate checks leaf before queueing; SessionHost.active checks session ID/file. Check navigation after async dispatch and before reporting; ordinary branch appends advance leaf and must not be mistaken for a branch switch. Distinguish UI receipt, host delivery, coder action, job completion and spoken acknowledgement.
- Speech barge-in invalidates pending speech/playback, not admitted coding calls or jobs. live.stop closes mic/provider/playback and preserves jobs; jobs.stopWork requests current-session work cancellation with acknowledged/pending/error reporting. If both requested, voice stop first. SessionHost.confirmDelegatedAgentStop requires trusted confirmation once delegation was delivered because tool origin is not attributable: preserve this guard for delegated stopWork. Transcript, tool output and observed jobs cannot grant cancellation authority.
- Context/status returned to GPT-Live must be bounded and sanitized: no private reasoning, raw tool output or false finality. Derive async feedback from verified host task updates/list/inspect, scoped to branch and delegation where possible. Generic job observations cannot be assigned to a delegation by guess. Close old observers and stale audio epochs so late status is not spoken on a new connection.
- extension.ts currently blocks GPT-Live in provider selection/start and UI. Re-enabling settings alone is not integration: start/stop ownership, typed routing, fallback errors and restart/navigation cleanup need an end-to-end path. Legacy protocol modules are historical, not production wiring.

## Tests to require (offline first)

1. Real extension path with fake GPT-Live socket and fake coding model: selected coding model, one Pi session/branch, one delegated work item, ordinary registered execute and permission denial/result hooks; typed and spoken context visible, no duplicate coder turn or direct-owner collision.
2. Partial/corrected/out-of-order fragments, offset boundaries, duplicate/replayed delegation IDs, changed args, disconnect/reconnect and navigation during dispatch: exactly once or explicit unknown outcome; never silently re-run or label ASR authoritative.
3. Async shell/job launch, finish after voice stop or interruption, status return to live conversation, stale speech suppression and branch-scoped observation; distinguish queued/running/done/acknowledged, avoid raw output leaks.
4. Plain barge-in, voice-only stop, work-only stop, both in order; trusted stop confirmation denial/approval, pending/partial stop reports and foreground self-stop during execute. Voice stop preserves jobs; work stop does not quietly kill voice.
5. Host branch append versus true navigation, startup failure/late callback, typed input while speech is active, transcript persistence/restart, bounded context and image/large-result limits. Test compiled extension/CLI integration, then real provider/device acceptance separately; mocks do not prove spoken UX.
