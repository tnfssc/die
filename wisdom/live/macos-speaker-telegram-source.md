## More than an enabled flag

- [tg_owt audio_transport_impl.cc L204-L238](https://github.com/desktop-app/tg_owt/blob/be39b8c8d0db1f377118f813f0c4bd331d341d5e/src/audio/audio_transport_impl.cc#L204-L238): the actual render callback requests a 10 ms block, mixes far-end audio, feeds **that mixed frame** to ProcessReverseAudioFrame, then resamples/copies for device output. This is a concrete software AEC reverse reference, not a second mic input and not provider output that has merely been queued seconds ahead.

## Comparison/action

Die's native helper supplies its far-end source to the same Apple AVAudioEngine output as its voice-processing input, but delegates the entire reference/delay/adaptive-processing path to Apple. It has no equivalent explicitly observable reverse-stream APM call. Absence of a software reverse-stream call is **not itself a bug** when using Apple's platform AEC. Telegram demonstrates a concrete alternative architecture if measured Apple output remains unsuitable; adopting it would require 10 ms framing, actual rendered reference, capture/render latency tracking, device routing and avoiding double AEC. Copying only echo_cancellation=true is not an implementation.

No correction justified by this comparison alone. First compare die's post-processed capture against rendered speech and distinguish provider interruption from local flush/failure. Any software APM prototype must be isolated, not a hurried framework replacement in the working startup/job bridge. Do not substitute muting, playback holdoffs, or VAD threshold changes for speakerphone cancellation.
