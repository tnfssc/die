# SSH workspaces: where execute actually runs

Research only, 2026-09-26. No code changed. Web lookup used installed authenticated `tvly` CLI (`tvly search` and `tvly extract`); source links below. This is a design recommendation, not an agreed product spec.

## Constraint and current shape

Ordinary execute JS must see the remote machine: `import { stat } from "node:fs/promises"; await stat("./file")`, `Bun.file`, `require()`, module lookup and child processes. SSH-wrapping only `shell()` fails this contract: `node:fs` and Bun APIs still run against the local kernel and cwd. A mounted filesystem alone does not make process execution or dependency loading remote.

Verified in this checkout: `src/typescript/execution.ts` spawns a fresh `process.execPath` execute runner with `cwd`, inherited/scrubbed environment, piped stdout/stderr, image pipe and private IPC for job helpers; termination signals its local process group. `src/typescript/runner.ts` resolves imports/packages by reading the cwd's `node_modules` and `package.json`. `src/typescript/job-bridge.ts` uses framed request/reply over child-process IPC. `src/tasks/task-manager.ts` launches and tracks shells/agents as local processes, records bounded output and kills process groups; `src/typescript/extension.ts` ties execute to session identity, cancellation and job delivery. `ARCHITECTURE.md` gives execute worker/IPC to typescript, background jobs to tasks, and session authority to session. `PRODUCT.md` Phase 3 and Unified execute API describe isolated execute and session-owned asynchronous jobs. `wisdom/values.md` favors simple existing boundaries, truthful state, safe user work and bounded resources. These are repository findings, not claims about SSH support today.

## Designs

1. **Entire die agent runs on SSH host; local terminal is an SSH client.** Simplest *first usable mode* if user accepts remote model sessions and credentials: SSH into host, install compatible die/Bun and invoke die in a remote PTY (possibly just document `ssh -t host 'cd /path && die'` first). Runner, `node:fs`, shell, child agents, git/worktrees, history and jobs all share one remote cwd and machine, with no new execute proxy or split scheduler. Local UI is then just terminal forwarding; mic/live/web and client integrations may need separate work and must not be claimed local. API/provider tokens and session history live remotely; remote machine gets those credentials. SSH private key remains local. On connection loss, remote foreground PTY may receive hangup and jobs may die or persist depending on how launched; existing die shutdown semantics must be tested, not promised as resumable. To preserve sessions across disconnection requires an explicit remote supervisor/tmux or detach/reconnect protocol, not just SSH.

2. **Local agent/UI with remote workspace runtime and job service.** Best coherent design *if local UI, voice or local model credentials are requirements*: install a version-matched remote die workspace host (Bun/packaged runtime plus execute runner and task service) under remote user. Local agent/session authority talks through SSH stdio or a loopback remote socket tunneled over SSH using a small versioned framed protocol. Send execute source, cwd, limits, cancellation; receive output/images/status; send job operations; run `shell`, subagents, worktree setup and path-sensitive tools on that host too. Plain JS runs in remote Bun, so `stat` and package imports work naturally. A local LLM orchestrator can keep API credentials local, but remote child agents either need credential forwarding via a bounded authenticated channel or remote credentials; avoiding remote model keys means more protocol and provider streaming complexity. Define job IDs scoped to remote host/session; remote service owns task process groups/output and durable-or-explicitly-ephemeral state, local side owns notification delivery. A lost SSH link is **unknown**, not completed or stopped; reconnect/reconcile by ID, distinguish reply receipt from job acceptance, avoid blind re-execution of mutating requests. Remote service process lifetime and storage policy are real additional work. Existing in-process IPC and TaskManager cannot be copied across SSH by merely changing spawn arguments.

3. **Local agent plus filesystem/API proxy.** Remote file RPC can support selected `readFile/stat/writeFile` calls and remote shell, but cannot transparently replace all synchronous/async `node:fs`, Bun filesystem APIs, native addons, dynamic imports, package resolution and arbitrary spawned tools in ordinary JS. Monkey-patching modules or SSHFS leaves local execution, OS differences and identity ambiguity. Only reasonable if product narrows the API to explicit remote file tools, which contradicts the stated ordinary-execute requirement. Do not recommend as transparent SSH workspaces.

## Outside evidence and limits

- VS Code [Remote SSH](https://code.visualstudio.com/docs/remote/ssh) runs UI-facing extensions locally and most workspace extensions on SSH host; opens a remote folder and installs its server there. Its [Remote Development FAQ](https://code.visualstudio.com/docs/remote/faq) explicitly says workspace extensions get remote source, filesystem and APIs via a remote extension host/server; server download can fall back to local download and transfer. **Verified:** split UI/workspace execution is a workable precedent, not evidence die already supports it or must duplicate its protocol.
- VS Code [remote troubleshooting](https://code.visualstudio.com/docs/remote/troubleshooting) describes a remote server connection key, remote-user-readable key file, shell-derived remote environment and remote download/proxy pitfalls. **Inference for die:** authenticate any daemon/socket even inside SSH and consider login-shell environment and offline installation; VS Code's key mechanism need not be copied.
- JetBrains [remote development overview](https://www.jetbrains.com/help/idea/remote-development-overview.html) puts source and backend IDE on remote host and connects a local client over SSH. **Verified analogy**, not a dependency recommendation.
- OpenSSH [ssh(1)](https://man.openbsd.org/ssh) and [ssh_config(5)](https://man.openbsd.org/ssh_config) document SSH transport/configuration, port forwarding and multiplexing. **Inference:** prefer user's SSH config/agent/host-key verification and an SSH-carried stdio channel initially rather than exposing a public daemon; SSH gives transport security, not job persistence or RPC idempotency.

## Recommendation / decisions still needed

Start with option 1 as an honest remote mode or proof of product fit; it already meets the hard execute semantics with the fewest moving pieces. If the intended UX specifically needs a local die TUI/voice, local provider credentials or switching local/remote workspaces inside one session, choose option 2 and make remote runtime + task service the unit of placement; don't implement shell-only SSH as a half-step marketed as remote execute. Preserve SSH key/known_hosts on local client, use explicit remote install/version checks, and state where provider keys, history, output and project files live. Test on a host without outbound internet and on a dropped link, including `stat`, dynamic imports, `Bun.file`, shell, subagents, cancellation and reconnect. Unknowns requiring product decisions: local UI versus remote PTY; remote OS/architecture/runtime support; whether remote provider/network access is allowed; whether sessions/jobs must survive disconnect; where persistent history belongs; and acceptable remote install/update footprint. No evidence these are already requirements.
