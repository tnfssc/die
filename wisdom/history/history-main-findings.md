# Main release review finding — pending fix

The first-assistant publication collision was reproduced. A pending manager had a user entry, then another file was created at the reserved public session path. Appending the assistant entry threw EEXIST. `DiskEntryStore.append` added metadata, cache state, and `hasAssistant` before publication threw. `SessionManager._appendEntry` only updated the skeleton and leaf after `store.append` returned. As a result, `getEntries()` included the failed assistant entry while `getLeafId()/getBranch()` still pointed to the user entry. The target sentinel stayed intact, but the manager indexes split. Repro: `/tmp/die-history-publish-repro.ts`.

The pending append and metadata must roll back when publication fails, or both views must stay in sync another way. Prefer a transactional append. Once the link succeeds, treat it as committed even if cleanup unlink fails. Do not roll back an authoritative file that is already public. Add a regression for exclusive publication collision and recovery. Main will implement this after the history owner returns, or coordinate a narrow edit if needed.
