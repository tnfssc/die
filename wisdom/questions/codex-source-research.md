## Short answer

Do not treat “Codex asks, keeps working independently, then prominently asks again when blocked” as one established Codex behavior. **There are two different tools.** The older `request_user_input` waits for a response at the tool call; the newer, catalog-gated `request_user_input_async` emits an async question item, returns `{"accepted":true}` immediately, and lets the model continue that turn. That is evidence for *asking while continuing*, not for a durable unanswered question or a later prominent prompt. A September 2026 desktop bug report says the async question card vanished on turn completion. The user's recollection of a later prominent prompt may describe a particular client/model flow, but I found no source that promises it.

## Sourced behavior, with dates

- **Official app-server docs** ([Codex App Server, read 2026-09-26](https://developers.openai.com/codex/app-server#toolrequestuserinput)): `tool/requestUserInput` is an experimental server request for 1–3 short questions, with a free-form option. The [same section](https://developers.openai.com/codex/app-server#toolrequestuserinput) says app-server emits `serverRequest/resolved` when the client replies **or** the pending request is cleared at turn start/completion/interruption. `autoResolutionMs` can tell a host client to resolve after a timeout; it is not a promise that every client uses the same timeout.
- **Synchronous tool, public source at [2026-09-26 commit e72da2b](https://github.com/openai/codex/commit/e72da2b53805894878023d01949a25a082e0a5cb):** [handler lines 64–91](https://github.com/openai/codex/blob/e72da2b53805894878023d01949a25a082e0a5cb/codex-rs/core/src/tools/handlers/request_user_input.rs#L64-L91) rejects non-root agents, checks allowed modes, sets `is_blocking` in Plan mode, and awaits `session.request_user_input` before returning answers to the model. [Tool schema](https://github.com/openai/codex/blob/e72da2b53805894878023d01949a25a082e0a5cb/codex-rs/core/src/tools/handlers/request_user_input_spec.rs#L22-L127) asks for 1–3 short questions with choices and adds a free-form Other option. Allowed modes depend on configuration; do not claim it is always Plan-only or always available in Default. `is_blocking` is a protocol distinction, not proof the model can run past an awaiting tool call.
- **Async tool, official release note:** [Codex CLI 0.153.0, dated 2026-09-03](https://developers.openai.com/codex/changelog) says structured asynchronous questions via `request_user_input_async` are supported **when enabled by the model catalog** (PRs [#42151](https://github.com/openai/codex/pull/42151), [#42178](https://github.com/openai/codex/pull/42178)). In [the async handler at the same pinned commit](https://github.com/openai/codex/blob/e72da2b53805894878023d01949a25a082e0a5cb/codex-rs/core/src/tools/handlers/request_user_input_async.rs#L113-L149), it emits an `AgentMessage` with `delivery: Async` and structured questions, then returns `{"accepted":true}`; it does not await an answer. [Integration test](https://github.com/openai/codex/blob/e72da2b53805894878023d01949a25a082e0a5cb/codex-rs/core/tests/suite/request_user_input_async.rs#L376-L505) checks the turn continues and the tool output reaches the next model request. This is a supported path, not proof every model, runtime, or UI enables or preserves it.
- **Caution from a real client:** [openai/codex issue #43803, opened 2026-09-08](https://github.com/openai/codex/issues/43803) reports three reproductions in ChatGPT desktop 26.901.51231 on macOS: in Default mode the async question card appeared during work but disappeared as the final answer rendered, so the user could not answer. This is one user's report, not a general guarantee or independently verified fix. [Issue #28969, opened 2026-06-18](https://github.com/openai/codex/issues/28969) reports a 60-second auto-accept of a recommended Plan-mode answer in CLI 0.141.0; it is also a report, not a universal default.
