## Findings, smallest corrections

1. **Do not put ledger JSON in a visible chat entry.** The in-progress `src/questions/runtime.ts:30-37` calls `pi.sendMessage({customType:"question-answer",display:true,content:"Saved answer ..." + JSON.stringify(question) ...})`. That is precisely the raw metadata/chat flood class caught by the prior real GPT Live PTY regression (`wisdom/live/gpt-live-tui-rendering.md:9-19`: 25 JSON bubbles before, zero after). Keep the saved answer accessible to the model and a concise human acknowledgement, but make internal continuation content non-displayed; inspect the **actual** source CLI and web transcript replay rather than assuming `details` hides the `content`. If a visible item is necessary, render only a short answer status, not owner/version/dedup JSON or instructions to the model.
2. **Agent tool contract contradicts authorization.** `src/prompts/execute-description.md:5` and `src/typescript/job-bridge.ts:98-111,331-336` advertise `questions.answer({id,owner,version,text})`; in-progress `src/questions/runtime.ts:78-80` explicitly rejects tool answers and directs human CLI `/questions answer`. Remove the model-facing answer affordance or explain its genuinely permitted caller; show usable `ask/list/get/cancel` examples and parent-only/child unsupported behavior without exposing an unusable method. The current API forces `blocked:true` for every question (`src/questions/service.ts:120-124`), while the proposal explicitly asks for an immediate non-blocking post and a later explicit block (proposal, “Recommended smallest contract”). Verify intended scope; do not describe it as general asynchronous posting unless supported.
3. **CLI controls have a discoverability mismatch.** `src/questions/extension.ts:57-100` shows a compact status `N questions pending` and commands for list/detail/answer/cancel/resume, but the command description and repeated usage strings omit `resume`; the visible list prints full opaque ID and status plus text, with no short action hint. Include `resume` in help if supported, and one concise discovery cue (e.g. `/questions`) with the pending status or list, not a subtitle or repeated paragraphs. Keep ordinary pending in the normal status color; reserve warning for genuine errors. `src/questions/extension.ts:39-59` swallows refresh failures by clearing the badge; verify a corrupt/unavailable ledger cannot masquerade as zero pending. The generic `Too many active questions` from `src/questions/service.ts:137-139` should say cap and next action (answer/cancel a pending question) if it reaches user/agent.
4. **Do not claim web or voice reply acceptance from CLI code.** In-progress `src/questions/runtime.ts:78-80` says web projection and child in-place replies unsupported; `wisdom/questions/implementation.md` says no web support claim without projection tests. Voice transcripts must not become implicit answers. The proposal's CLI-and-web list is not yet evidence of web implementation. State this scope plainly in release notes, or implement/test the missing surfaces if they are part of release scope.
