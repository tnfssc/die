## Actual handoff and bridge

- The execute tool runs isolated Bun code; its per-call bridge dispatch accepts `handoff`, validates nonempty message, records it, aborts **foreground waits** but not managed jobs (`src/typescript/extension.ts:79-129`). The worker's `handoff` returns no answer: after bridge acknowledgement it throws `HandoffSignal` (`src/typescript/job-bridge.ts:73,300-306`); the runner catches it to finish execution (`src/typescript/runner.ts:327-337`). Successful result is rendered as a handoff and marked `terminate: true` (`src/typescript/extension.ts:136-179`). Normal final response also yields the user turn (`src/prompts/execute.md:22`). This is a **turn boundary**, not a suspended await that resumes with the next user's answer. Code after handoff does not run.
- Bridge methods exported by worker are shell/subagent, handoff, history, goal, live.stop and jobs list/inspect/input/stop/stopWork/snooze/setWatch (`src/typescript/job-bridge.ts:69-110,300-326`); request IDs/pending promises are socket-local (`src/typescript/job-bridge.ts:270-298`). Shell spawns a manager-owned subprocess, defaults to 3s wait, returning foreground result or background identity (`src/tasks/job-service.ts:290-310`). Local agents have independent session files and subprocesses (`src/tasks/job-service.ts:402-449`); native scoped agents use durable invocation/call fingerprint and server launch identity (`src/tasks/job-service.ts:323-365`). Job listing merges local manager inventory and remote native tasks; inspect uses local bounded buffer or remote observe (`src/tasks/job-service.ts:668-750`). Foreground completion owns its response only once bridge acknowledges it; disconnect transfers notification ownership (`src/tasks/task-manager.ts:452-510`). It is not appropriate to count a launch ACK as job completion.

## Attention and UI

- One in-memory attention scheduler per manager tracks running jobs, default quiet 5 min and review 10 min, watch enabled by default, snooze bounded, drops state at completion; each notice verifies pending/inspects bounded output (`src/tasks/job-attention.ts:4-5,60-108,119-135,174-209,241-309`). Local completion/attention batches use Pi `sendMessage(... deliverAs: 'steer', triggerTurn: true)` when no Live owner; Live owner is routed separately (`src/agent/extension.ts:239-282`). Print/json mode holds idle `agent_end` for completion/attention, not the spawning tool (`src/agent/extension.ts:575-639`). RPC native T3 avoids volatile Pi steer delivery and persists/dispatches notices through server; local command notices use T3 local delivery (`src/agent/extension.ts:285-315,575-584`). Raw `die_task_event` is telemetry from manager events for web adapter, not a turn or answer (`src/agent/extension.ts:402-405`; `src/t3/tasks/events.ts:1-40`).
- CLI task monitor is an in-session modal showing running jobs, selected bounded inspection/output and stop confirmation (`src/ui/task-monitor.ts:186-240`; `src/tasks/task-monitor.ts`). This is observation/control, not a user-question inbox. Native child lifecycle cards and delegated child routes are web projections: patch keeps lifecycle cards unfolded and avoids redirecting a temporarily missing child route (`integrations/t3/upstream/die.patch:10818-10882,11107-11144`); client projection applies server events (`integrations/t3/upstream/die.patch:12099-12132`). Composer input/new-thread routing is a separate web action (`integrations/t3/upstream/die.patch:10883-10959,11425-11570`). Do not infer from the visible card that a question reply is correlated to a pending execute call.

## Ownership, continuity and voice

- Local manager lives with session and on shutdown terminates running children, escalates with watchdog (`src/tasks/task-manager.ts:581-615`). Child session transcript and worktree/branch are separately durable artifacts; worktree creation resolves a pinned Git source and writes a dedicated workspace, with optional t3.json setup (`src/tasks/job-service.ts:509-565`; `src/tasks/worktree-workspace.ts:141-150`). A branch/worktree survives the agent turn; this does **not** imply an in-flight local process, scheduler timer, socket promise or modal survives process restart. Native scoped tasks live in T3 server task ledger, can be observed/listed after parent turn; their parent/child thread projections and completion delivery are server-owned (`src/tasks/job-service.ts:323-365,668-750`; `integrations/t3/upstream/die.patch:1533-1542,1977-2053`). Navigation changes which web thread is viewed, not job ownership. Same-branch checks protect Live on branch navigation (`src/live/main-owner.ts:167-173`). Check actual server retention/restart deployment before promising indefinite native continuity.
- Live acquires ordinary canonical Pi main session only while text agent idle and tool loadout execute-only (`src/live/main-owner.ts:143-195`); execute calls remain main-owner foreground, delegated work remains child-owned. Live speech interruption clears provisional drafts, interrupts playback/provider response, **does not cancel jobs** (`src/live/main-owner.ts:569-589`; `src/live/extension.ts:91,251-266`). Explicit stop-work aborts foreground and requests child cancellation; `live.stop` is separate (`src/typescript/extension.ts:111-121`). Completed voice input is captured into canonical session, typed input is handled by Live when owned (`src/live/main-owner.ts:404-427`; `src/agent/extension.ts:669-682`); provider transcript interruption is not a durable answer. In paired mode delegated main turn uses canonical `sendCustomMessage(... triggerTurn: true)` and forwards resulting assistant text back to voice (`src/live/main-owner.ts:497-525`). CompletedInput is a one-use TTL authority for sending *received* voice text, not an answer-to-question matcher (`src/session/input.ts:16-40`).

## Answer-returning question primitive? Scoped finding

- Searched exported execute globals/bridge, job service dispatch, task/attention, Live owner, and pinned T3 patch for ask/request-input/question paths. No **Die execute API** found that suspends an invocation across a user turn and resolves with a correlated reply; handoff terminates and fresh user input starts a new turn. This is scoped evidence, not a claim that no API exists anywhere. The pinned upstream patch contains an existing `user_input_request` turn-item test fixture with `questions` (`integrations/t3/upstream/die.patch:8238-8247`): upstream may support provider-specific user-input requests, but this does not show a Die bridge method, durable request/reply binding, or Live voice routing. Inspect actual upstream provider contract/runtime before designing around or denying that facility.

## Implications for a proposed question workflow

A UI question card, an assistant handoff message, a child task attention notice and a true request/answer RPC are distinct contracts. Need explicit durable request identity, owner thread/branch and reply authorization/correlation, pending/answered/cancelled semantics on restart/navigation, and foreground-vs-child cancellation policy if a future answer-returning API is desired. Do not hold the isolated execute socket waiting across a user turn or treat spontaneous speech interruption as cancellation. Existing values already cover truthful state, bounded resources, durable handoff and ownership; no values edit needed for this survey.
