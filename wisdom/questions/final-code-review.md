## Release blocker: reply dispatch has no durable at-most-once claim

`src/questions/runtime.ts:54-76` adds the reply key only to an in-memory set, invokes `pi.sendMessage(... triggerTurn:true)`, then asynchronously writes `delivery:"delivered"`. If the process exits, or the write fails, after sendMessage accepts the turn, disk still says `queued`. A fresh runtime projects that as `resume-needed` (lines 26-28); `/questions resume <id>` (lines 190-209) accepts it and sends another turn. Even without failure, a restart between the synchronous send and asynchronous write has the same result. The message includes a reply ID, but no consumer deduplication of that ID is shown, and the visible prompt asks the model not to replay earlier calls rather than enforcing idempotency. This violates the explicit no-duplicate-continuation acceptance criterion; it is not solved by the in-memory `delivered` set or by the service's idempotent answer mutation. Persist an attempted/uncertain dispatch claim *before* sending, and either make consumer acceptance idempotent by reply ID or prohibit blind resends after uncertain acceptance; explain uncertainty honestly rather than treating `queued` as proof no turn happened. Test crash/write-error after send and explicit resume. Do not equate sent with model completion.
