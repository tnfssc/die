# Persistent questions implementation review (2026-09-26)

Scope: independent architecture/test review, **not** an implementation or passing-test claim. Read `wisdom/values.md`, `wisdom/questions/persistent-questions-proposal.md`, `wisdom/questions/die-architecture-survey.md`, and production-path files cited below. No implementation was edited. Contracts from the backend/API and CLI workers were not yet available, so I did not add speculative tests.

## Release-critical findings

1. **Web support remains unproven.** Production web is pinned T3 source + `integrations/t3/upstream/die.patch` (`integrations/t3/README.md`, `build/build.ts`). No upstream web checkout was present in this worktree, so I read the *actual maintained production patch*, not a complete compiled web application. `apps/web/src/components/ThreadRouteView.tsx` patch hunk (patch lines 10830–10882) keeps delegated child URLs hydratable after missing shell; `apps/web/src/session-logic.ts` and `apps/web/src/components/chat/MessagesTimeline.logic.ts` patch hunks (11736–11758, 11107–11144) preserve provider command lifecycle cards. `packages/client-runtime/src/state/orchestrationV2Projection.ts` patch hunk (12099–12132) updates turn usage only. None demonstrates a pending-question field, subscription, detail projection, renderer, or answer command. Existing transcript cards cannot stand in for an actionable persistent inbox. **Do not announce web support from a backend endpoint or CLI test alone.** Gate it with a test that uses the built/pinned web projection and UI path.
2. **Child ownership must be explicit.** `src/tasks/job-service.ts` distinguishes local manager children and server-owned native scoped tasks; `src/tasks/task-manager.ts:581-615` kills running local children on shutdown. A native child question must either be owned by its own server thread with a supported reply continuation or explicitly marked parent-only/unsupported; do not attach a reply to whichever thread is currently displayed. In the proposal, parent continuation is supported and native child in-place reply is not. Child completion while parent waits for a question must not overwrite the question or silently wake a blocked/paused parent. Server native completion dispatch in patch lines 7181–7320 has projection-based current-delivery checks; a question wake must also revalidate durable reply ID and eligibility at admission, not only at scheduling.
3. **Live cannot treat speech as answer or stop.** `src/live/main-owner.ts:404-427,497-525,569-589` handles final transcript/typed input, serialized delegated canonical turns, and provisional transcript interruption separately; `src/agent/extension.ts:239-315` routes completion into the Live owner or durable T3 delivery, and `src/typescript/extension.ts:111-121` separates stop-work from live.stop. Targeted explicit answer command should persist before any wake. Barge-in and a provisional transcript must not answer/cancel/auto-resume; `live.stop` alone must not stop jobs. Question status must be visible after voice interruption and reconnection.
4. **Navigation is not authority.** The child-route fix above merely hydrates a thread; `apps/web/src/hooks/useHandleNewThread.ts` and `apps/web/src/lib/chatThreadActions.ts` patch hunks (11425–11570) address composer/new-thread intent, not answer targeting. Reply must carry original question ID, owner thread/branch and version; changing displayed branch/thread or opening a child URL between rendering and clicking reply should never reroute it to the new active thread. Re-fetch on conflict, never silently post answer as ordinary chat on another branch.

## Test recommendations, prioritized

- **Production web projection integration + browser smoke** (required before claiming web support): seed pending question via real server command in thread A; subscribe to server snapshot/events in the pinned patched client; verify visible actionable question survives several progress messages, terminal assistant output, websocket reconnect and page reload; switch to thread B/child URL and back; answer from UI and assert exactly one saved reply belongs to A, correct version, no unsolicited B turn. Recreate client from snapshot to prove persistence, not just optimistic local state. Exercise both an event received live and one missed while disconnected. Verify answer is disabled/removed on cancel/resolution and stale-version conflict is shown. Test actual built web runtime (or its production projection+UI components), not an invented parallel frontend store.
- **Background completion/blocked boundary**: post two pending questions; block parent explicitly on Q1; let local or native child finish Q2-independent work. Assert completion remains durable and observable, Q1 remains pending, parent does not resume solely for job notice or rerun a handled completion; answer Q1 once; assert one eligible continuation consuming saved reply ID, no duplicate continuation after retry/restart. Include answer/child-complete race and child-complete/stop-work race. Cross-check print/json hold logic `src/agent/extension.ts:575-639` and server completion delivery patch 7181–7320; neither is itself an answer protocol.
- **Native ownership**: from native child post/request question, navigate parent/child, attempt reply and confirm explicit unsupported child in-place continuation or specified parent route (never ambiguous success); test native task completion arriving after parent answers, after parent pause, and after server restart. Do not infer process survival from durable child transcript/worktree.
- **Live**: question pending while voice owner active; interrupt provisional speech and verify no answer; explicit typed targeted reply while owned should persist once and queue safe canonical turn; stop voice only and confirm jobs/question survive; explicit stop-work cancels only per its contract and never silently accepts a pending reply. Switch branch while queued delegated turn to verify `sameBranch` rejection does not lose durable answer and reports resume needed.
- **Race/identity matrix**: reply vs cancel, duplicate reply idempotency, stale version, limits, missing owner after restart, answer from alternate surface, parent user pause/stop, and reconnect snapshot. Every API ACK must represent saved mutation, not a successful model continuation; an ineligible/restart case must report 'answer saved; resume needed'.

Review limitations: upstream full `apps/web` source was not checked out here; patch hunks and existing architecture survey are evidence for current maintained modifications, not a running web E2E. No contracts or question implementation existed in this worktree when reviewed; no tests were run. Revisit these checks when integration changes land. The lessons are already in values 3/4/8/10 (single ownership, durable handoff, truthful UI, useful evidence); no values edit from this review.
