# Stable v0.8.0 preparation (no automatic preparation publish)

Use the Release workflow's **Run workflow** on the intended commit first. It runs the macOS arm64 native helper tests/build, Linux checks and four stable raw binary builds, then uploads a `stable-release-candidate` Actions artifact; it does not create or push a tag or release. Inspect the checksums and source metadata and test the downloaded candidate on supported hardware before any tag. The artifact is for review only, not an updater URL.

After review, a maintainer may tag the *same commit* v0.8.0 and push it explicitly; this workflow publishes only on stable tags after both jobs pass. Do not tag a failed or unreviewed candidate. Prerelease tags are skipped (the experimental rc assets have a different layout). Existing updater clients expect the unchanged raw asset names die-linux-x64, die-linux-arm64, die-darwin-arm64, die-android-arm64 and matching .sha256 files, not a tarball. Only darwin-arm64 embeds the Mach-O arm64 Live Lab helper. Source, notices and license files accompany the assets.

Mac CI covers ASan/UBSan C ring tests, helper --self-test, a device-free protocol hello, and compiled CLI --version/--help; Linux runs the full deterministic and web test matrix. Before a public stable release, manually verify on a real Apple Silicon Mac that the *candidate release binary* extracts/runs its embedded helper and returns protocol-v1 hello under a fresh HOME without repository files. Also validate opt-in microphone permission, device routing, echo/interruption/latency with headphones and provider credentials supplied only by the tester. CI does not exercise a real mic/speaker or provider, nor signing/notarization. Confirm the old v0.7.1 updater resolves the raw asset and checksum names without changing its behavior.
