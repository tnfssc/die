Voice is not the whole agent

Why can’t we just swap in GPT-Live?

Because “can talk” and “can own a coding task” are different jobs. The catch is how work gets handed from the voice model to the tools.

The short answer

GPT-Live-1 is a real API model, not a discontinued product. Its documented path hands reasoning and tool work to a backend. Today, die’s direct voice-main-owner path expects the voice model itself to request an executable tool call and continue with its result. GPT-Live’s client handoff notification does not provide that request. A deliberately designed backend agent could work—but it is a different architecture, not a model-name switch.

01 / The job

Picture an ordinary spoken coding request.

You say: “In the settings page, make the Save button disabled while the request is running, and add a test.” The assistant needs to inspect files, edit code, run tests, and tell you what happened. Speech alone cannot change a repository.

Hear the task. Understand the request and decide what files matter.

Act with permission. Ask die’s execute tool to inspect or edit files and run a focused test.

Continue from evidence. Read the tool result, perhaps fix a failed test, then speak an honest summary.

03 / The missing piece

A handoff signal is not an execute request.

What the client notification gives

A delegation event identifies that a handoff occurred and where it sits on the conversation timeline. Documented metadata identifies the delegation and its target/type and response association.

Think “the voice agent has handed off here,” not “edit this file with these exact arguments.”

What it does not give

It does not carry the user’s request text or tool arguments. It cannot by itself tell die which command to execute, with what parameters, under whose task authority.

A backend handler would need to assemble conversation and application context and decide what to do. A partial speech transcript is not an authorized arbitrary-code command.

But the model card says “Function calling: Supported.” That is a capability label, not evidence of direct named tool calls from the live voice frontend to die’s execute path. The delegation guide describes tool calls inside the separately configured Responses backend; their arguments and results belong to that backend flow. Both statements can be true.

04 / Who is in charge?

A backend agent does not have to mean two competing bosses.

A sound design can give each part a narrow role: GPT-Live listens, speaks and manages conversational timing; one canonical task/session authority owns reasoning, tools, permissions, history and cancellation. Replies flow back as feedback—not as a second independently authorized coding plan.

That design needs explicit ownership of typed input, transcript uncertainty, tool-result continuation, reconnects, and cancellation. Current die production selection does not implement that GPT-Live path. The restriction is die’s current architecture, not a law that GPT-Live cannot be integrated.

05 / Controls & tradeoffs

“Wait—” is not “cancel the tests.”

Interrupt speech

Stop or redirect the spoken response. Work already handed to an agent or running job may continue. Do not infer cancellation from silence.

Stop Live

Turn off this session’s microphone/playback/provider connection. In die’s current control contract, live.stop() preserves jobs.

Cancel work

Use the separate stop-work control. jobs.stopWork() requests scoped job cancellation and reports what was acknowledged or pending; its report is not proof every job exited.

Direct path

Fewer reasoning handoffs can make ownership simpler; actual responsiveness and spend depend on model, audio duration, tool calls and implementation.

Delegated path

A backend adds another reasoning/context handoff and potentially another billable model or workflow. It may offer stronger task specialization. No measured cost or latency comparison is claimed here.

06 / Evidence & limits

What is known, and what is still a design question.

Documented / observed in source

  • OpenAI documents GPT-Live delegation to a Responses backend or application workflow; client notification is metadata rather than request text and tool arguments.
  • The GPT-Live model card marks function calling “Supported.” The delegation guide places described tool calls in the backend path.
  • Current die source exposes Gemini and Realtime choices, not GPT-Live, in the production picker; direct-main work treats execute as the owner’s tool.

Not established here

  • No connected GPT-Live coding-tool integration or comparative latency/cost measurements are presented.
  • The single-authority backend layout above is a proposal, not evidence it is implemented or tested.
  • No exact provider event payloads or provider runtime behavior beyond the linked documentation are asserted.
