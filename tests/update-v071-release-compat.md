# v0.7.1 updater compatibility fixture

Run: `bun test tests/update-v071-release-compat.test.ts` (Bun >= 1.4.1, local v0.7.1 git tag). No network, API, mic, install or publish is used. The test extracts the **unmodified** tagged `src/update.ts` and `package.json` into a temporary directory and pins the updater source SHA256 to `589cf75c8bf9dc20f537128ca10ae84b90b7b7a03e9c4f0014578d61e4d4a259`. Only `fetch`, `compiled`, version, platform, architecture and a temporary executable path are injected via the tagged updater's public dependencies. All fetched URLs remain the official latest-release API and v0.8.0 download URLs; response bytes come from temporary staged local release files (four raw asset names and four .sha256 files). Temporary targets are never the executing process.

Fixtures are intentionally synthetic, with format magic and an embedded 0.8.0 label. The preflight rejects wrong version or tar-shaped fixture bytes; the updater rejects release metadata advertising a tarball in place of a raw asset. **Important limitation:** v0.7.1 itself does *not* validate binary format/version, only the checksum and raw asset name. A tarball served under the raw name with its own valid matching checksum would pass the updater. These tests do not prove actual 0.8.0 executables boot, nor real GitHub publication, and especially do not prove the macOS arm64 executable runs: that requires a Mac runner using real staged release assets.
